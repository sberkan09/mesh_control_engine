# M-LIGHTNINGBOLT — Strikes with a place: a visible bolt and thunder from the real distance (milestone record)

**Status:** planned 2026-10-22 (steps 11a to 11d; 11c only if 11b finds no existing draw path that fits). **Owner: routine 2 thread (the M-VISUAL line).** Follow-up of M-RAINFX (7e `ThunderDelay`, whose note says the strike distance is derived because `LightningStruck` has no position) and M-WEATHERAUDIO. Today a storm flashes: `kit_lightning` raises `Weather.flash_mul`, the whole sky brightens uniformly, there is no bolt, and thunder distance is only the delay ticks the strike was given. No Linear issues (free issue limit); this record is the tracker.

**Goal.** Every strike gets a deterministic world position near the camera, the event carries it, `ThunderDelay` uses the real distance, and a jagged emissive bolt (plus an optional brief point light at the strike) is drawn for the flash ticks. Opt-in, saved, deterministic; a scene without the new component, without `Lightning` or without a Storm hashes and renders exactly as today.

**Not in scope:** a new shader or render pass (11c exists only as a fallback), forked branches beyond a simple optional side fork, a directional flash (the sky stays uniformly lit; `Weather.flash_mul` is untouched), thunder variety or echoes, strikes that damage or ignite things (no physics hook), bolts hitting real geometry (the strike point is a computed ground position at `ground_y`, no raycast), changing the `Lightning` component bytes, new audio assets.

## Design

- **Opt-in component, not new `Lightning` fields.** New component `LightningBolt` (`mce/kit/lightning_bolt.h`, one per scene, the first in ECS order drives, registered by `install_precipitation`). Adding saved fields to `Lightning` would change the hash of every scene that has a `Lightning` (samples and goldens), so the new state lives on a component that existing scenes do not have. Authoring: `min_range_m` 150 and `max_range_m` 900 (Range 10..5000, swapped if inverted), `ground_y` 0, `height_m` 600 (top of the bolt above `ground_y`, Range 50..3000), `width_m` 1.5 (Range 0.05..20 at 100 m; scaled with distance so far bolts keep a readable angular width), `segments_log2` 5 (2^5 = 32 segments, Range 2..7), `jitter` 0.25 (midpoint displacement as a fraction of segment length, Range 0..0.6), `fork` 1 (0/1: one side fork from a hashed mid-point, half length), `light_intensity` 0 (0 = no point light), `light_radius_m` 400, `enabled` 1. Engine-written and saved: `strike_x`, `strike_z` (f32, the last strike's ground position), `strike_dist_m` (f32), `strike_id` (u32, the `Lightning.counter` value of that strike), `active` (u32: flash ticks left, mirrors `Lightning.remaining` at the strike), explicit padding, zeroed (`state_hash` hashes raw bytes), padding-audit entry. A plain bolt is a pure function of `strike_x/z`, `strike_id` and the authoring.
- **Position (kit, 11a).** `kit_lightning` is not rewritten in behaviour: when a strike happens and a `LightningBolt` exists, the new code (a helper `bolt_strike_position`, in `lightning_bolt.cpp`, called from the same system right where `LightningStruck` is pushed) derives, from `hash_mix(Lightning.seed, counter * 4 + 2)` and `+ 3`, a bearing in [0, 2*pi) and a range in [min_range, max_range] (uniform; the hash is a separate stream from the existing `counter * 2` and `counter * 2 + 1` ones, which stay exactly as they are, so the strike times and delays of an existing scene do not move). The origin is the primary camera position at the strike tick (the same camera lookup `ThunderDelay` uses); with no `Camera3DComponent` the origin is (0, 0). Position = origin + range * (sin, cos) on the ground plane. The bolt's world position is then fixed at the strike (it does not follow a moving camera), as the sky is far away and a strike is a place. All trig in f64, stored as f32.
- **Event (11a).** `LightningStruck` gets three appended fields: `u32 has_pos` (0), `f32 distance_m` (0) and `math::vec3 pos` (0). Existing `LightningStruck{delay}` constructions (tests, the Luau demo test) keep compiling and mean "no position". With a bolt, `thunder_delay_ticks` is set to `max(1, ceil(distance_m / 343 / dt))`, no longer clamped to 30..300 (the range limits bound it to 4 to 15 s at 60 Hz). `distance_m` is the 3D distance from the camera to the strike point at the strike tick.
- **ThunderDelay (11a).** With `has_pos` set it uses `distance_m` for both the delay (at its own `speed_mps`, with the existing `ceil` and 1e-6 rule) and the attenuation, instead of `thunder_delay_ticks * dt * 343`. With `has_pos` 0 it is bit-identical to today (the old path stays and keeps its tests). So a changed `speed_mps` now changes the delay for a positioned strike, while a strike without position keeps ignoring it. No new state in `ThunderDelay`.
- **Fan-out check (done while planning).** `scripts/ci/include_fanout.py` reports 11 of 805 TUs for `precipitation.h` and 11 for `thunder_delay.h`, far below the walls warning of 150. Changing the event struct in `precipitation.h` therefore does not need a seam PR first; 11a may carry it. The new header `lightning_bolt.h` is included only by the extract, the install and the tests. If 11a's own run shows the fan-out above 150, split the event change into a seam PR, but it should not.
- **Bolt geometry (kit, 11b).** A pure function `build_bolt(const LightningBolt&, f32 sx, f32 sz, u32 id, vec3* out, u32 cap) -> count` in `lightning_bolt.cpp`, with no state: a start point at (sx, ground_y + height_m, sz) offset sideways by a hashed few metres, an end at (sx, ground_y, sz), and deterministic midpoint displacement for `segments_log2` rounds. Each round displaces every midpoint perpendicular to the segment by `jitter * segment_length * (2h - 1)`, where h is `hash_mix(id, round_index_and_segment) / 2^32` in f64 and the perpendicular is built from the strike's bearing and the vertical (a fixed rule, no random rotation drift), halving the displacement scale per round. Output is at most 2^7 + 1 points, a fixed-size array; the optional fork is a second, shorter polyline from a hashed mid-point. No allocation per frame beyond a small fixed buffer, no wall clock, no float accumulation across frames.
- **Draw path (extract, 11b).** The bolt reuses an existing path, no shader. Order of preference, decided by 11b reading `Kit3DExtract` and `MeshStore`: (1) emissive stretched boxes: one `MeshInstance` per segment of a unit box mesh the extract uploads once under `MeshStore::allocate_key()` (the `writable_` store, as the static merge does) with a `MaterialOverride` whose emissive is white, scaled to width x length and rotated along the segment, `emissive_tint` set to an HDR colour (pushes into bloom), `cast_shadows` false, tint black so only the emissive shows; (2) if (1) is not usable (no writable store, a lit-only material), a chain of `render::ParticleEmitter` bursts along the polyline (additive, HDR colour, `size_start` from the width, `lifetime` of the flash, speed 0, one emitter id range reserved for the bolt) fed through `add_particle_emitter`; (3) only if neither draws a continuous bright line, 11c adds a pass. Intensity follows `Lightning.remaining / flash_ticks` (full on the first flash tick, then a short falloff, with a hashed one-tick re-strike flicker at the second tick, a pure function of `id`). Nothing is drawn when `active` is 0, `Weather.current` is not Storm, `enabled` is 0 or the quality tier is Low (a cheap `QualitySettings` check; a new cvar is not added, the existing weather tier switch is reused). Optional point light: one `PointLight` (`scene.add_point_light`) at the middle of the bolt, colour blue-white, intensity `light_intensity * falloff`, radius `light_radius_m`, no shadows; it exists only when `light_intensity` > 0. The extract does not write any component, so the state hash is unaffected by drawing (a test hashes with and without the extract).
- **Save and load.** `LightningBolt` holds only the last strike and the flash counter; `Lightning` already saves `remaining`. A save during a flash resumes with the same bolt and the same hash, and N ticks after the load equal N ticks without it.
- **If a render pass is needed (11c, fallback only).** The two reuse paths above are expected to cover a bolt. If 11b proves neither does (for example a sky-only ribbon that must draw behind clouds), 11c adds a minimal pass: **Opus writes the shader, with independent Opus review, as in M-CLOUDS 9b**, behind a uniform that is zero for a frame without a bolt so every golden stays byte-identical, with a pixel test and a `lightning_bolt` golden. Otherwise 11c is dropped (as 10b was in M-WEATHERAUDIO) and 11d becomes 11c.
- **Luau.** `weather.set_bolt{min_range=, max_range=, height=, width=, segments=, jitter=, fork=, light=, light_radius=, enabled=}` and getters (authoring plus read-only `weather.bolt_distance()`, `weather.bolt_pos()` returning x, z, and `weather.bolt_active()`); named errors, values clamped to the Range, nothing written on error, typed in `definitions.cpp`. `samples/12_weather` gets a `LightningBolt`, with `light` off, and logs the last strike distance every 150 ticks (its entity count is unchanged, a component is added to an existing entity; the golden and log expectations are updated in the step, nothing else moves).

## Gates
- A scene without `LightningBolt` (or without `Lightning`, or never in a Storm) has an unchanged state hash and unchanged frames; every existing sample hash and golden stays byte-identical until 11d changes `samples/12_weather`, and only that sample's expectations move.
- The strike times and `thunder_delay_ticks` of a scene with `Lightning` are identical with and without `LightningBolt` (the position uses its own hash stream), except that with a bolt the delay is the real distance and not the hashed 30..300.
- A positioned strike's thunder delay equals `ceil(distance_m / speed_mps / dt)` ticks and its gain follows `distance_m`; a strike without position behaves exactly as today (the existing `test_thunder_delay.cpp` cases pass unchanged).
- Save and load in the middle of a flash resume on the same state hash and the same bolt vertices; N ticks after the load equal N ticks without it. Two runs of `samples/12_weather` stay deterministic.
- Padding of `LightningBolt` is explicit and zeroed (padding audit); the bolt is a pure function of saved state, so drawing writes nothing.
- Include fan-out of `precipitation.h` stays under the walls warning (checked with `scripts/ci/include_fanout.py`; 11 TUs at planning time, so no seam PR is needed first).
- No shader or pass is added unless 11c is taken; if it is, the review and golden rules of M-CLOUDS 9b apply.
- Luau: setters clamp, bad types raise named errors and write nothing.
