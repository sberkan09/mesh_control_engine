# M-DYNRES — Dynamic resolution scaling: the render scale follows the measured GPU frame time (milestone record)

**Status:** 46a to 46d done (2026-11-07; data seam, pure controller, quality tiers and cvars; the `Forward3D` driver, the `DynamicResolution3D` component, its feed and the player's capture rule), 46e and 46f planned. Steps 46a to 46f in three PRs (46a+46b, 46c+46d, 46e+46f). **Owner: routine 2 thread (the M-VISUAL line).** Follow-up of M-VISUAL2 2 (`Forward3DDesc::render_scale`, the spatial upscaler, sharpen and the TAA temporal upsample: the machinery that makes a frame drawn below the output size look acceptable), M-PERF (the GPU timestamps and `gpu_ms` in the perf capture that this milestone reuses as its sensor), M-VIEWS (split-screen and render-texture views, whose budget rules it must respect) and the 3D visual assessment (`assessments/3d-gorsellik-degerlendirmesi.md`, performance). Today the scale is a constant: `QualitySettings::render_scale` (Low 0.67, Medium 0.85, High 1.0) is copied into `Forward3DDesc::render_scale` once, when the player starts the 3D path (`player.cpp` `init_3d`), and `Forward3D::record_view` reads it every view. Nothing adjusts it from what the frame actually costs, so a scene that overruns its budget (a heavy volumetric night scene on a weak GPU, a fourth split-screen cell, a sudden explosion of particles and lights) keeps dropping frames for as long as it lasts, and the only remedy is the player choosing a lower tier by hand. No Linear issues (free issue limit); this record is the tracker.

**Naming:** no type, file, cvar or milestone called `DynRes`, `dynres`, `dynamic_res`, `DynamicRes`, `DynamicResolution` or `M-DYNRES` exists (`git grep -niE 'dynres|dynamic[ _-]?res|resolution scal|adaptive res'` over the whole tree, 2026-11-07: no hit at all). The only related names are `Forward3DDesc::render_scale`, `QualitySettings::render_scale`, `kit::scale_view_quality` (a per-view quality cut by window share, a different thing: it turns features off, it never changes a resolution) and `Upscaler`. The render setting is `render::DynamicResolution` (in `PostFx::dynres`), the pure controller lives in `mce/render/dynres.h` (`dynres_*` functions, `DynResParams`, `DynResState`), the kit component is `DynamicResolution3D` (`mce/kit/dynamic_resolution.h`), the cvars are `r.dynres`, `r.dynres.target_ms` and `r.dynres.inject`. Re-grep right before 46a: a milestone added in the meantime may take the names.

**Goal.** An opt-in controller that keeps the 3D frame inside a GPU time budget by moving the render scale. Every frame the first view of the frame reads the newest completed GPU timestamps (a few frames old, see below), turns them into a smoothed, scale-independent cost, and picks the render scale for the *next* frame: down at once when the frame overruns `target_ms`, up one 1/16 step at a time and only after a cooldown and with headroom. The scale is quantized to 1/16, bounded by a floor and by the tier's own `render_scale` (the ceiling), rate limited, and has hysteresis, so it does not oscillate. The frame is drawn smaller and reaches the output through what already exists: the bilinear or spatial upsample, TAA's temporal upsample, the sharpen. **Render-side only: nothing is written to a component and nothing is hashed; the simulation never reads the scale.** With `PostFx::dynres.enabled` false (the default), no `DynamicResolution3D`, or `r.dynres 0`, the code path is the one of today and the frame is bit-identical; with it on but never over budget the scale never leaves the ceiling, which is `render_scale` itself, so that frame is bit-identical too. With a fixed injected cost (`r.dynres.inject`) the scale sequence is a deterministic function of the schedule and the frame count, and is tested on the CPU.

**Not in scope:** a different upscaler (FSR, DLSS or any vendor SDK; the existing bilinear, spatial and TAA paths are what is scaled), CPU-bound frames (the controller reads GPU time only; a frame that is slow on the CPU does not get cheaper by drawing fewer pixels, and the controller does not look at `frame_ms`), per-cell scales in split-screen (one scale for the frame's window views, see the views section), dynamic resolution of render-texture views (they keep the tier's static scale), scaling of the 2D and UI passes (they draw at output size, always), lowering below the renderer's own 0.5 clamp, dynamic quality features (turning SSR, volumetrics or shadow cascades off under load: `scale_view_quality` and the tiers already own that axis; this milestone moves resolution only), a mip or LOD bias that follows the scale (a follow-up), a GPU-timestamp fallback built on CPU time (no timestamps: the controller holds the scale), and a Luau API beyond the component fields.

## Investigation (what the code does today; the plan below rests on these facts)

- **Where the scale lives.** `Forward3DDesc::render_scale` (`forward3d.h`, default 1) is renderer-global and set once: `quality_settings(tier).render_scale` through `apply_quality(const QualitySettings&, Forward3DDesc&)` in `quality.cpp`, called from `Player::init_3d` before `Renderer::init_3d(fd)`. `Forward3D::desc()` is const and there is no setter. The per-view application is the start of `Forward3D::record_view` (`forward3d.cpp`): `scale = clamp(desc_.render_scale, 0.5f, 1.0f)`, `size = lround(viewport * scale)` (min 1), `ensure_targets(size)`, then `post_source_ = hdr_; post_size_ = size`. The view's `scene.view().viewport` is the output size. So every 3D view of the frame, render-texture views included, uses the same scale today.
- **Can it change every frame?** The value yes, the cost no. `ensure_targets(size)` returns at once when the size is unchanged, otherwise `destroy_targets()` frees the MSAA and resolved HDR, depth, LDR, the half-size AO/SSR targets, the velocity targets, `fin_src_`/`fin_up_`, the bloom chain **and the TAA history** (`history_[0..1]`, `history_valid_ = false`, `ssr_prev_valid_ = false`) and creates them again. The RHI retires the old textures `MCE_FRAMES_IN_FLIGHT` (3) frames later, so a step briefly holds two sets in VRAM, and a TAA frame after a step restarts its history. Buffers that are sized from `post_size_` check their own size and are recreated lazily (`fx_`/`fx_size_`, `flare_occ_`, `fin_src_`, the shafts buffer at half of `post_size_` by the first view that draws shafts and its `shafts_buf_used_` rule, `outline_dst_` by the frame's first view, `trans_src_`). The TAA history is at the **output** size (`record_taa` compares `history_size_` with `view.viewport`), not at the render size, and the jitter is derived from `size`, so keeping the history over a scale-only change is valid (it is exactly what temporal upsampling does); only `destroy_targets` throws it away. Per-view slots (`ViewState`, `MCE_FORWARD3D_VIEW_STATE`) each hold their own `size_` and targets, so two views of one frame can legally run at two scales.
- **Upsampling at a scale below 1.** Without TAA the tonemap pass reads `post_source_` bilinearly (`post_size_ != out`), with `Upscaler::Spatial` (`r.upscaler`) an edge-adaptive 4x4 upsample runs after it from `fin_src_`, and `sharpen` (`r.sharpen`) runs last at output size; with TAA the resolve upsamples temporally to the output-size history. At scale 1 (`post_size_ == out`) the spatial upsample is skipped and the tonemap reads texel-exact: the step from the last grid scale to 1.0 therefore also switches the upsample kernel (a look limit, see risks).
- **GPU time to the CPU.** `Forward3D::timestamp(cmd, stage)` writes `desc_.timestamp_base + stage` for the frame's first view only (`out_.first`): 16 stamps from `kTsBegin` to `kTsFxaa`, so `Forward3D::gpu_times(ts)` and `Forward3DGpuTimes::total` are the **first 3D view's** span. The device keeps them per frame slot and `RenderDevice::last_gpu_timestamps()` returns the newest completed set (`GpuTimestamps::frame_index`, `ms(from, to)`), `MCE_FRAMES_IN_FLIGHT` = 3 frames behind (GL collects a slot's queries when `begin_frame` reuses it, after its fence). Only the player's perf capture consumes them today (`Player::attach_gpu_times` writes `perf::Frame::gpu_ms` and `gpu_stage_ms`; the whole-frame span `kFrameTimestampBegin/End` is written only under `-perf_capture`). Backends: GL and Metal have timestamp queries, SDL GPU has none and fakes them (`caps().fence_timestamps`: a fence per stamp and a waiter thread, "minus the GPU's idle time between submits", coarser), WebGPU has none (`caps().timestamp_queries` false); the editor's preview renderer sets `timestamps = false`. `RenderDevice::frame_index()` gives the current frame, so a ring of (frame, scale) lets a sample be matched with the scale its frame drew at.
- **Determinism rules in force.** Rendering is outside the state hash and the replay; the player already uses fixed render dt in capture runs (`capture_due()`). A measured GPU time differs on every run and machine, so the scale it drives is nondeterministic by nature: therefore the scale must never reach the simulation, the replay, the state hash, a component, the Luau API or a golden. Goldens and captures stay byte-stable because the default is off and because a run with no timestamps (headless, fixtures with `timestamps = false`, the editor preview, WebGPU) holds the ceiling scale.

## Design

- **Render setting (seam, 46a).** A POD `render::DynamicResolution` in `scene3d.h` just above `PostFx`, and `DynamicResolution dynres;` in `PostFx` after `shafts`. Fields (ranges `apply_quality` clamps in 46b; NaN falls back to the default): `bool enabled = false` (off draws the frame as today); `f32 target_ms = 14.0` (4..100: the GPU budget of the 3D frame, a little under 16.7 so the 2D, UI and present work fits at 60 Hz; `r.dynres.target_ms` overrides it per player); `f32 min_scale = 0.6` (0.5..1: the floor; the renderer's own clamp stays 0.5); `f32 max_scale = 1.0` (min..1: an extra ceiling below the tier's); `f32 headroom = 0.15` (0.05..0.5: the scale goes up only while the estimate at the next step stays below `target_ms * (1 - headroom)`, the hysteresis band); zeroed `u8 pad_[3]`. `scene3d.h` and `forward3d.h` are over the 150 warning, so 46a is the seam PR for both, data only, merged first, with the `include_fanout.py` numbers: `Forward3DStats::render_scale` (f32, the scale this view drew at, 1 when 1:1), `dynres` (bool, the controller ran this frame) and `dynres_cost_ms` (f32, the smoothed measured cost, 0 when none); in `Forward3D` a forward declaration `struct DynResState;` and a pointer member `dynres_` to it (created in `init`, freed in `shutdown`; the type stays out of the header, as `Forward3DPassU`), the private `update_dynres(const Scene3D&)` declaration, and `ensure_targets(rhi::Extent2D size, bool keep_history = false)`. `dynres.h` is **not** included by `forward3d.h`.
- **Why the controller lives in `Forward3D`.** It owns the device (so `last_gpu_timestamps()` and `frame_index()`), the stamps, the scale application and `ensure_targets`; the player needs no new per-frame plumbing, the editor and the MCP app get the same behaviour for free where they have timestamps, and the setting travels in the scene's `PostFx` like every other render setting. The cost of that choice is that the first view's scene decides (the frame's one controller reads `scene.post().dynres` of the frame's first view); a later view's setting is ignored, recorded.
- **Pure CPU controller (render, 46b).** Narrow header `mce/render/dynres.h` (math only, forward-declares `struct DynamicResolution;`), bodies in `src/dynres.cpp`; f32, fixed evaluation order, no `rand`, no clock, no global state; a NaN or infinite input is a rejected sample (the scale holds):
  - **Cost model.** A frame costs `ms = c * ((1 - v) + v * s^2)`: a fixed part (shadows are not resolution bound, the 2D/UI/upsample at output size) and a part that follows the pixel count, `v` = `kDynResVariableShare` 0.7. `f32 dynres_cost_full(f32 ms, f32 scale, f32 v)` returns `c`, the cost the same frame would have at scale 1, so smoothing across scale changes is valid; `f32 dynres_ms_at(f32 c, f32 scale, f32 v)` is the forward direction; `f32 dynres_scale_for(f32 c, f32 target_ms, f32 v)` the largest continuous scale whose cost fits (`sqrt(max((target / c - (1 - v)) / v, 0))`, 1 when `c <= 0`, clamped 0..1).
  - `f32 dynres_quantize(f32 scale, f32 floor, f32 ceiling)`: the grid is `k / 16` for the integers in `[floor, ceiling)` plus **the ceiling itself exactly** (the tier's 0.67 is not a multiple of 1/16, and "never over budget" must give back the tier's own scale, bit for bit); the result rounds **down** to the grid (never overshoots the budget), `floor` snapped up to the grid, `floor > ceiling` gives the ceiling.
  - `struct DynResParams { f32 target_ms, floor, ceiling, headroom; u32 max_down_steps = 4; u32 down_cooldown = 8; u32 up_cooldown = 60; f32 ema = 0.25f; f32 spike = 2.0f; f32 variable_share = 0.7f; }` and `struct DynResState { f32 scale; f32 cost; u32 cooldown; u32 samples; }`.
  - `f32 dynres_step(const DynResParams&, DynResState&, bool has_sample, f32 sample_ms, f32 sample_scale)`: (1) a valid sample is converted to `c`, clamped to `spike` times the current smoothed `c` (a one-frame hitch from a shader compile or an asset load does not halve the resolution), blended by `ema` (the first sample seeds it); (2) the cooldown counts down by one; (3) **over budget** (`dynres_ms_at(c, scale) > target`): the new scale is `dynres_quantize(dynres_scale_for(c, ...))`, at most `max_down_steps` grid steps below the current one (a rate limit that still sheds 25 % of the width in one move), and the cooldown becomes `down_cooldown` (so a second drop can follow soon if one step was not enough, but not on every frame); (4) **under budget with headroom** (`cooldown == 0` and the estimate at the next grid step up is `<= target * (1 - headroom)`): exactly one step up, cooldown `up_cooldown` (60 frames: recovery is slow on purpose); (5) otherwise the scale holds, which is the hysteresis band between "fits" and "fits with headroom". No sample (no timestamps yet, the backend has none) holds the scale and does not advance the cooldown past 0. Returns the new scale; `DynResState::scale` starts at the ceiling.
  - `bool dynres_resolve(const DynamicResolution&, bool cvar_on, f32 cvar_target_ms, f32 tier_floor, f32 tier_ceiling, DynResParams& out)`: false (the controller does nothing, the frame is today's) when the setting is off, `r.dynres 0`, the tier says no, or any input is not finite; otherwise the clamped params: `target_ms` = the cvar when `> 0` else the setting's, `floor` = max(setting, tier floor, 0.5), `ceiling` = min(setting `max_scale`, `tier_ceiling` = the tier's `render_scale`).
  - `struct DynResInject` and `bool dynres_parse_inject(StringView text, DynResInject& out)` / `f32 dynres_inject_ms(const DynResInject&, u64 frame)`: the test injection, a schedule `"22@0,9@200"` = "the frame costs 22 ms at scale 1 from frame 0, 9 ms from frame 200" (up to 8 entries, frames ascending; a malformed string parses to nothing and logs once). The injected sample for frame `k` is `dynres_ms_at(cost, scale_of_frame_k)`, delivered at frame `k + MCE_FRAMES_IN_FLIGHT` through the same ring a real timestamp takes, so a CPU test sees the real latency, and the model's own recovery (cost falls as the scale falls) is exercised.
- **Quality tiers + cvars (render, 46b).** `QualitySettings::dynres` (all tiers true: the tier's `render_scale` is the ceiling, so the Low tier can still shed from 0.67 toward the floor) and `dynres_floor` (Low 0.5, Medium 0.5, High 0.65: the best tier does not drop to a visibly soft picture), in `quality.cpp`. Cvars next to `r.sun_shafts`: `r.dynres` (bool, Saved, "Dynamic resolution scaling (PostFx::dynres; off = the fixed render scale)"), `r.dynres.target_ms` (float, Saved, 0 = the setting's, otherwise 4..100: the player's own budget, e.g. 8 for a 120 Hz display) and `r.dynres.inject` (string, not Saved, empty = measured: the fake-cost schedule above, a test and sample hook, documented as such). `apply_quality(const QualitySettings&, ShadowSettings&, PostFx&)` clamps the setting's ranges (NaN to the default) and turns `enabled` off for `r.dynres 0`; the cvars are read every frame.
- **The driver (46c, `forward3d.cpp`).** `Forward3D::update_dynres(scene)` runs once a frame, on the frame's first view (`out_.first`), before the scale is read in `record_view`:
  1. `dynres_resolve(...)` from `scene.post().dynres`, the cvars and the tier numbers (`desc_.render_scale` is the ceiling and `desc_.dynres_floor`, the 46a field next to it that `apply_quality(q, desc)` fills from `QualitySettings::dynres_floor`, is the tier's floor). False: `dynres_` state is dropped (the next enable starts at the ceiling) and the scale is `desc_.render_scale`, today's line, untouched.
  2. The sample: with `r.dynres.inject` set, the injected cost as above; otherwise `last_gpu_timestamps()`, only when `frame_index` is newer than the last sample consumed, `gpu_times(ts).total` of that frame (the first 3D view's span) **times the number of 3D window views recorded that frame** (a split-screen cell costs about its share of the area, so N cells cost about N times the first; an estimate, recorded), and the scale of that frame from a 4-entry ring of `(device frame_index, scale)` filled when a frame's scale is chosen (a sample whose frame is not in the ring is skipped).
  3. `dynres_step(...)` gives the scale for this frame; it is stored in the state and becomes the first view's scale and every later window view's.
  4. **Application.** `record_view` takes `scale = out_.linear_output ? clamp(desc_.render_scale, 0.5f, 1.0f) : dynres_scale_` (the old clamp stays as the guard). A window view therefore follows the controller, a render-texture view keeps the static tier scale. `ensure_targets(size, keep_history)` is called with `keep_history` true when only the render size changed and the output size did not: `history_[]`, `history_size_` and `history_valid_` survive `destroy_targets`, so a dynamic step does not restart TAA (the one-frame softness that remains is the history being blended at a new jitter density; a test bounds it). `ssr_prev_valid_` still drops for one frame (the SSR trace is half size and its history is in the old resolution).
  5. Stats: `stats_.render_scale` (every view), `stats_.dynres` and `stats_.dynres_cost_ms` (the smoothed `c` converted to ms at the current scale). One `MCE_LOG_INFO` per change, `dynres: scale 1.0000 -> 0.8750 (cost 19.4 ms, target 14.0 ms)`, rate limited by the cooldowns (at most one line per 8 frames); the sample test greps it.
  6. No new shader, pipeline or draw path.
- **Kit component: `DynamicResolution3D`, opt-in and separate (kit, 46d).** Choice and reasons: the pass must be off by default so every golden and sample stays byte-identical, and a scene must be able to say "my budget is X ms". `Environment3D` (in `kit3d.h`, wide and `Save`d, so a field would also move the scene format) is the wrong home; the quality tier is the wrong home (a tier is the player's, a budget is the scene author's, the cvars are the player's override); a runtime cvar alone cannot be authored into a scene and cannot be covered by the capabilities and sample checks. So the one new thing is a small, opt-in component in its own header `mce/kit/dynamic_resolution.h` (the shape of `LensFlare3D`, `HeatHaze3D` and `SunShafts3D`; the first enabled one by entity index is read; registered by `install_kit3d`; **`kit3d.h` stays untouched**). Fields (all `Save`): `enabled` 1, `target_ms` 14 (4..100), `min_scale` 0.6 (0.5..1), `max_scale` 1 (min..1), `headroom` 0.15 (0.05..0.5), explicit zeroed `pad_`. No runtime state and nothing hashed. `Kit3DExtract` (`.cpp` only) fills `post.dynres` from the first enabled component and runs it through `render::apply_quality`. Because the controller reads the first view's `PostFx`, a scene that wants it puts the component next to its primary camera's world entity like the other post components.
- **Interaction with views (M-VIEWS).** Window views, split-screen cells included, draw at `cell size x scale` with the **one** frame scale: the controller sees the frame's total 3D cost and moves a single number; `scale_view_quality` (which cuts features by a view's window share) keeps working on top and is independent (resolution on this axis, features on that one). Per-cell scales are a follow-up (one controller per slot needs per-slot samples and a slot-wise cost split, which the single-view timestamps do not give). Render-texture views (`linear_output`) keep the static tier scale: they are small, often rate limited (`due`), a monitor whose resolution pops would flicker on screen, and their cost is part of the frame total the controller already sees. The `Renderer`'s upright staging copy for render textures is sized by the output viewport, not the scale, and is unaffected.
- **Interaction with TAA, the upscaler and the sharpen.** With TAA the history stays valid over a step (see 46c above) and the resolve upsamples to the output-size history, so dynamic resolution is smoothest there and High (TAA on) is the tier it matters most for. Without TAA the frame goes through the bilinear or spatial upsample (`r.upscaler`), and `sharpen` always runs at output size, so none of those need to know the scale; `post_size_` already carries it. The shafts, flare, haze, lens rain and underwater passes use `post_size_`-sized buffers that re-check their size every frame, so a step costs them one recreate, not an error (a GL case pins the shafts buffer's `shafts_buf_used_` rule over a dynamic step).
- **Determinism.** The scale is a pure function of the setting, the cvars, the tier, the injected schedule or the measured stamps, and the frame counter. It never reaches the simulation: no component is written, no `Rng` is touched, the state hash and the replay do not read it; a kit test hashes a world with and without the component over a run (46d). With it off the old code path runs unchanged (no state, no ring, no timestamp read). Captures, goldens and film mode must not depend on the machine: 46d makes the player hold the ceiling scale in `-capture`, `-capture_tick` and the golden/sheet paths unless `r.dynres.inject` is set (the injected schedule is deterministic, so a capture with it is reproducible).

Checklist: the off-check (an off setting or `r.dynres 0` records no state, read no timestamp and touch nothing per frame), that "on and never over budget" is bit-identical to off (the ceiling is `render_scale` exactly, the grid never rounds it), the order (the controller runs on the frame's first view before `record_view` reads the scale, one controller per frame, a later view's setting ignored), the frame ring (sample matched with the scale its frame drew at; an unknown frame skipped; a repeated `frame_index` consumed once; the latency of `MCE_FRAMES_IN_FLIGHT` frames respected so the controller does not chase its own step), the cost model and the scale-independence of the smoothed cost (a step must not look like a cost change), the hysteresis (no oscillation between two steps at a cost on the boundary), the rate limits and cooldowns, the multi-view cost estimate, render-texture views on the static scale, `keep_history` (history handles, size and validity survive only a scale-only change and are destroyed on an output-size change; no leak, no double free; the per-view `ViewState` swap carries them), every size-checked buffer (`fx_`, `fin_src_`, the shafts buffer and `shafts_buf_used_`, `outline_dst_`, `flare_occ_`, `trans_src_`) recreated exactly once per step, no handle freed that was recorded earlier in the same frame (the deferred destroy of the RHI covers textures, but check the descriptor-like uses), the floating-origin and `reset_history` paths unaffected, nothing written to the TAA history that depends on the scale, the injection delivered through the same ring as a real sample, the capture rule, and that no state of the controller is hashed or reaches a component. To save CI cycles: 46a+46b one PR, 46c+46d a second, 46e+46f a third (the M-SUNSHAFTS shape). ## Gates

- With `dynres.enabled` false, no `DynamicResolution3D`, or `r.dynres 0`, every existing golden and sample hash is byte-identical through 46e. With the setting on but the frame never over budget, the frame equals the off frame bit for bit (the ceiling is `render_scale`). Audit in 46c: no existing scene sets the component, and no controller state exists for a default `PostFx`.
- Wide headers touched only in 46a (`scene3d.h`, `forward3d.h`); `dynres.h` is included only by `dynres.cpp`, `forward3d.cpp`, `quality.cpp`, the extract, the install and the tests. `kit3d.h` is **not** edited, and neither are `quality.h` (its `QualitySettings` rows are the one allowed edit, measured with `include_fanout.py` in 46b and said in the PR), `views.h`, `perf_capture.h` or any shader.
- Nothing is written to a component or the state hash; a kit test hashes the world with and without the component over a run with an injected overload (46d); two headless plays of the sample agree.
- Determinism of the scale: the same injected schedule gives the same scale sequence on the CPU controller and through `Forward3D` (GL test), twice.
- No thrash: over a 600-frame injected overload-and-recovery run the scale changes direction at most twice, never changes more often than the cooldowns allow, and every scale is a multiple of 1/16 or exactly the ceiling.
- No pop: a TAA step keeps the history valid, and the largest adjacent-frame pixel-mean difference over the step is under a bound stated in the test.
- GPU cases render one small frame (64x64 or 128x128); any case over 60 s ships a smoke variant and `mce_mark_slow`.
- Local checks before each push: `scripts/ci/local_ci.sh tidy` clean for the touched files, the new tests, and, after merging master, `--premerge` (walls, `capabilities --check`, the MCP transcript golden, `ctest -R` on the PR's own tests).

## Risks

- **The sensor.** GL and Metal stamps are real GPU time; SDL GPU's are fence based and coarser (they include per-submit granularity), and WebGPU and the editor preview have none, where the controller holds the ceiling by design. A controller tuned on GL may be too jumpy or too lazy on SDL GPU: the EMA, the spike clamp and the cooldowns are the levers, and the real-device check is row A19.
- **Latency.** A sample is 3 or more frames old, and a step takes effect the next frame, so the loop reacts in about 4 frames; the cooldowns and the scale-independent cost keep it from chasing itself, but a one-second load spike is only partly absorbed. Recorded; a shorter ring depth would help and is not this milestone's.
- **Target resizes are not free.** Each step recreates about two dozen textures and holds two sets for 3 frames of VRAM; with the cooldowns that is a few times a second at worst, but a hitch on the step frame is possible on a real driver. Mitigations in the plan: 1/16 grid, the cooldowns, `keep_history`. The real fix (allocate once at the ceiling and draw into a viewport) touches every pass that assumes uv 0..1 and is a follow-up.
- **Cost model.** `v` = 0.7 is a guess for a pixel-bound forward renderer with MSAA; a scene dominated by shadows or the compute passes gets less relief per step than predicted, and the controller then simply takes more steps (it re-measures every step). A per-scene `v` is a follow-up if it shows.
- **Multi-view cost.** The measured span is the first view's; N times it is the estimate for N window views. A split-screen with very unequal cells under- or overestimates; the injected-cost tests cannot judge it. Recorded; a frame-wide stamp pair is the follow-up.
- **Look.** The default `target_ms`, the floor of 0.6 and 0.65, the headroom, the cooldowns and the 1/16 grid are look and feel choices only a real display can judge; at the boundary 15/16 to 1.0 the spatial upsample is skipped (a faint sharpness change). llvmpipe pixels prove the sequence, the sizes, the history and the off checks. Goes to the GPU list (row A19).
- **CPU-bound frames.** If the CPU is the bottleneck the controller sees a cheap GPU and holds the ceiling, which is right; if the GPU is cheap but vsync is missed for other reasons, nothing is done. Recorded.
- **The ceiling is the tier.** On Medium (0.85) and Low (0.67) the controller can only shed below the tier's scale; it never raises above it. Intended; a player who wants more headroom picks a lower tier.
- **Texture detail.** A smaller frame samples textures at the lower resolution's LOD, so surfaces look softer than the same scale with a negative mip bias would; no bias is added. Follow-up.

## GPU verification

Headless (llvmpipe, lavapipe): the CPU controller's tests (46b) are exact; on the GL and SDL GPU fixture, off equals the plain frame exactly (setting, cvar, `timestamps = false`, no component) and on-but-under-budget equals it too; an injected overload steps `Forward3DStats::render_scale` down in grid steps with the HDR target's size following, the recovery returns exactly to the tier's scale, and the sequence equals the CPU controller's; a TAA step keeps the history valid with a bounded adjacent-frame difference; the shafts, flare and outline buffers survive a step; render-texture views keep the tier scale; split-screen cells scale together; the same run twice gives the same bytes; the sample's log shows the down and up sequence under `-r.dynres.inject`. Real-GPU behaviour (the measured sensor on GL and SDL GPU, no oscillation under a real load, the cost of a step, the look of the lowest scales with TAA and with the spatial upscaler) and Metal/WebGPU: row A19 of `/mnt/project-files/assessments/gpu-gereken-isler.md`.

## Deviations from the plan

- 46a: `Forward3D::dynres_` is a raw pointer that nothing creates or frees yet; 46c adds the `new` in `init` and the `delete` in `shutdown` (the type is incomplete in the header, so the delete lives in `forward3d.cpp` next to the first use).
- 46b: the plan's `dynres_step` lets a drop wait for the cooldown but also says an overrun is shed at once; as built a drop is allowed when the cooldown is 0 or when it was set by a rise (`cooldown > down_cooldown`), so an overrun right after a rise is not delayed, and a drop after a drop waits `down_cooldown` frames. No hidden state is added to `DynResState`. A step with no valid sample counts the cooldown down (floored at 0) and holds the scale.
- 46b: `dynres_parse_inject` does not log (the pure function holds no state); the 46c driver logs the single warning when it gets false from a non-empty string. Entries need frames strictly ascending and `ms` in (0, 1000]; before the first entry `dynres_inject_ms` returns the first entry's cost. The injected value is the cost at scale 1; the caller applies `dynres_ms_at` with the frame's scale.
- 46b: "the tier says no" in `dynres_resolve` is not a parameter: `apply_quality` already folds `QualitySettings::dynres` into `PostFx::dynres.enabled`. `dynres_resolve` also clamps the ceiling to 0.5..1 and the floor to 0.5..1.
- 46c: the driver state is created by the first enabled frame instead of in `init` (and deleted by the first off frame as well as in `shutdown`), so a renderer whose scenes never enable it holds no state at all; it is a file-local `DynResDriver` derived from `DynResState` (the ring, the consumed mark and the injection cache had to live somewhere, and `forward3d.h` was not to change). There is no separate `dynres_scale_` member: window views read the driver's `scale`.
- 46c: the injected cost is the frame's cost and is not multiplied by the window-view count (only a measured span is, since it covers the first view only). The injection schedule's frame clock is the controller's frame count since it was enabled (for the player, the first frame of the scene with the component), not the device frame index.
- 46c: on SDL GPU the fence timestamps of frame k are handed over as soon as its fence signals, measured on lavapipe as early as frame k + 1, not k + 3; the ring matches whatever frame a sample names (up to 4 frames back), so the controller sees a shorter latency there. The latency is not padded to 3 frames.
- 46c: a changed scale always logs; the cooldowns limit the lines to one per 8 frames except a drop right after a rise (the 46b rule lets that drop through at once), which can log within 8 frames of the rise.
- 46c (review): a frame whose first 3D view is a render texture (kit::record_views records render textures first, so that view writes the frame's GPU timestamps) gives **no measured sample**: its span is a view at the tier's static scale and says nothing about the window scale. Each ring entry records whether its stamps came from a window view (`stamped_window`, set on every `first` view; the last one wins, as the stamps do); the measured branch skips an entry without it and the scale holds. An injected cost is the whole frame's, so injection steps such frames as usual. A scene whose render texture is due every frame therefore never measures (recorded; the frame-wide stamp pair of the follow-ups fixes it). Two `first` views in one device frame whose scenes disagree on the setting: the later one decides for the rest of the frame (an editor-only case).
- 46d: the player holds the ceiling by setting `r.dynres` to 0 in a capture run (not `Forward3DDesc::timestamps = false`, which would also drop `-perf_capture`'s GPU times), unless `r.dynres.inject` holds a schedule that `dynres_parse_inject` accepts (review: a malformed one would make the renderer measure); an explicit `-r.dynres 1` on the command line that the hold overrides logs one `MCE_LOG_INFO` line. The player now includes `dynres.h` (6 TUs).
- 46d: neither the extract nor the install includes `dynres.h` (the extract needs only `render::DynamicResolution` from `scene3d.h` and `apply_quality`).
