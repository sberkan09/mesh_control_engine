# 7. 2D games

The 2D path is a set of scene-authored components (the "kit") that the player draws for you:
sprites, text, a camera, parallax layers, 2D lights, post effects, tilemap layers and particle
emitters. Your game code changes their fields; nothing in your module draws.

Units are metres with +Y up. An entity's `LocalTransform` places the sprite's pivot, its rotation
about Z turns the quad, and its scale multiplies `size`.

## 7.1 Sprites

| Field | Meaning |
|---|---|
| `texture` | the image; a null reference draws a solid quad in `tint` |
| `normal_map` | tangent-space normal map for 2D lighting (import with `srgb: false`) |
| `tint` | colour multiplier; `tint.a` fades the sprite |
| `size` | world size in metres; the texture is stretched to it |
| `pivot` | normalized, `[0.5, 0.5]` centre, `[0, 0]` bottom-left |
| `layer`, `order` | stacking: `layer` first (−100..100), then `order` within the layer, then ECS order |
| `flip_x`, `flip_y` | mirror |

A sprite shows its **whole** texture. There is no atlas region or sprite-sheet frame yet, so one
image per frame of animation and one `Sprite` per tile for tiled ground (or a tilemap layer).
Missing or broken textures draw as a magenta checker rather than nothing.

## 7.2 The camera

`Camera2DComponent` on an entity makes that entity's position and Z rotation the view:

| Field | Meaning |
|---|---|
| `pixels_per_meter` | 48 by default: a 1280 x 720 window shows about 26.7 x 15 m |
| `zoom` | 1 = one texel per pixel at `pixels_per_meter` |
| `clear_color` | the background |
| `primary` | the first primary camera in ECS order is the one rendered |
| `pixel_snap` | snap the view to whole pixels so pixel art stays crisp |
| `fit_width`, `fit_height` | fit mode: > 0 shows at least that many metres across / up on every screen (both set: the whole rect, the longer axis shows more); overrides `zoom` and its pixel-snap quantization; 0 = off |

On phones, use fit mode: without it the visible area follows the pixel count, so a 2400 x 1080
phone sees about 1.9 times the world a 1280 x 720 window does. `fit_height = 15` shows 15 m up on
any screen; wider screens show more width. Check layouts at phone sizes on desktop with
`-window 1080x2400` (chapter 16).

The player writes a `kit::ViewInfo` world resource before every tick: framebuffer size in
pixels, window size in points, display scale, safe-area insets, orientation, and the primary
camera's resolved view. `world.try_resource<kit::ViewInfo>()` reads it; its `touch_to_world`,
`mouse_to_world` and `screen_to_world` map `InputState::touch_points()`, `mouse_pos_px()` and
pixels to world metres. Headless runs write a fixed 1280 x 720 landscape screen so state hashes
stay deterministic; a game that reads it in windowed runs simulates differently per window size.

A follow camera is game code: a system in `FixedUpdate_Post` that moves the camera entity's
`LocalTransform` toward the player (Kindle's `CameraFollow` with `offset`, `min`, `max` and
`smoothing` is a complete example).

## 7.3 Animation

Animate by swapping the texture reference:

```cpp
void set_texture(kit::Sprite& s, const asset::AssetRef<asset::Texture>& tex) {
    if (tex.guid.is_null() || s.texture.guid == tex.guid) return;
    s.texture = asset::AssetRef<asset::Texture>{tex.guid, {}};
}
```

Keep the frame references as `AssetRef<Texture>` fields on your component (`idle`, `run_a`,
`run_b`, `jump`) so the editor sets them, and switch on a tick counter (`(ticks / 6) % 2` for a
two-frame run cycle at 10 fps). Resolved textures are cached per GUID, so swapping costs nothing
after the first draw.

## 7.4 Text

`TextLabel` draws world-space text from a cooked font asset: `font`, `text` (up to 63
characters), `color`, `height` in metres, `align` (left, centre, right about the entity's
position), `layer` and `order`. Your game writes `text` with `label.text.assign(StringView(buf))`.

Fonts are `.ttf` files cooked into an atlas; the sidecar's `size` is the baked pixel height, so
pick one that matches the on-screen size you need (26 px works for HUD text at 48 px/m).

**Screen-space HUD.** There is no HUD component. Put a `TextLabel` on an entity with
`Parallax {"factor": [0, 0]}`: it then stays fixed to the camera. Author it at the offset from the
camera centre where it should sit (for the default view that is ±13.3 m by ±7.5 m) and give it a
high `layer`. Kindle's `HudText` component marks which label shows what, and one system writes
the strings.

## 7.5 Parallax and backdrops

`Parallax` on an entity scrolls its sprite, tilemap or text against the camera by `factor` per
axis: 1 moves with the world, 0.5 is a far background, 0 is pinned to the camera, above 1 is a
foreground. `repeat_x` tiles a sprite endlessly across the view. Author the layer where it sits
when the camera is at the origin. A `factor.y` of 0 pins a sky vertically, which suits a sideways
scroller.

## 7.6 Lighting

Sprites with a `normal_map` are lit by `Light2D` entities; everything else ignores lights.

- `Light2D {"kind": "Point", "color", "intensity", "radius", "height"}` at the entity's position.
  At most 16 point lights touching the view are used, in ECS order.
- `Light2D {"kind": "Ambient"}` sets the base light every lit sprite receives (white when the
  scene has none).

Import normal maps with `srgb: false`. The `extras_2d` sample shows a lit scene.

## 7.7 Post effects

`Post2DComponent` on the camera entity adds three effects, each toggled by its own flag (all
off by default): `vignette` (`vignette_intensity`, `vignette_radius`, `vignette_softness`),
`color_grade` through a 256 x 16 LUT strip (`lut`, imported with `srgb: false`;
`render::make_identity_lut` makes a neutral one to edit) with `lut_strength`, and
`chromatic_aberration` (`aberration`). F7 in the player toggles post
effects for comparison (`-r.post2d 0` starts with them off).

## 7.8 Tilemaps

A `TilemapLayer` draws one `.mctilemap` asset (`map`) with its tile (0, 0) at the entity's
position; `tint` colours it and `layer`, `order` stack it like a sprite. The
asset holds the tileset texture, the grid cell counts and the tile indices; the editor's Tilemap
panel creates and paints it:

1. Select an entity, open the Tilemap panel, choose a tileset texture and the grid (columns, rows,
   width, height, tile size).
2. Press T (or "Paint tiles" in the View menu). Pick a brush cell from the tileset. Left drag
   paints, Ctrl erases, Shift+drag fills a rectangle.
3. Every stroke saves the asset and hot-reloads it.

Limits today: one layer per asset, no auto-tiling, no palette thumbnails, and the MCP server has
no tilemap tool (an agent paints by writing the `.mctilemap` JSON, section 5.7). A tilemap draws
only; give the ground a `Collider2D` on a separate entity (or several).

## 7.9 Particles

`ParticleEmitter` plays a `.mcpart` preset from the entity's position:

| Field | Meaning |
|---|---|
| `preset` | the `.mcpart` asset: texture, rate, lifetime, speed, direction and spread, gravity, drag, size and colour over life, blend mode |
| `seed` | per-emitter random stream (mixed with the entity index), so runs are reproducible |
| `playing` | emitting; clear it to stop while live particles finish |
| `destroy_when_done` | one-shots: destroy the entity when the last particle dies |
| `layer`, `order` | stacking like a sprite |

Particles are simulated on the fixed tick on the CPU and drawn as sprites in the same batch, so
they sort with sprites and cost one draw. From code, `f.resource<kit::ParticleSystem>().burst(e, n)`
emits `n` particles at once.

## 7.10 Stacking and sorting

Draw order is `layer`, then `order`, then ECS order (deterministic). Text draws above its layer's
quads. UI documents (chapter 12) draw on top of everything in screen space.

## 7.11 What the kit does not do

The kit draws; gameplay is yours. There is no player controller, pickup, hazard, goal, follow
camera or moving platform component in the engine. Ember Step's versions (`samples/03_platformer/
game/`) are spawned from code; Kindle's (`projects/Kindle/games/kindle/module/components.h`) are
reflected components a scene authors, and they are the recommended starting point: copy
`PlayerController`, `Coin`, `Hazard`, `Goal`, `Crumble`, `Mover`, `CameraFollow` and `HudText` with
their systems into your module and change what you need.
