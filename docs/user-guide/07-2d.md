# 7. 2D games

The 2D path is a set of scene-authored components (the "kit") that the player draws for you:
sprites, text, a camera, parallax layers, 2D lights, post effects, tilemap layers and particle
emitters. Your game code changes their fields; nothing in your module draws.

Units are metres with +Y up. An entity's `LocalTransform` places the sprite's pivot, its rotation
about Z turns the quad, and its scale multiplies `size`.

## 7.1 Sprites

| Field | Meaning |
|---|---|
| `texture` | the image; a null reference draws a solid quad in `tint` |
| `normal_map` | tangent-space normal map for 2D lighting (import with `srgb: false`) |
| `tint` | colour multiplier in **linear** RGB (see below); `tint.a` fades the sprite |
| `size` | world size in metres; the texture is stretched to it |
| `pivot` | normalized, `[0.5, 0.5]` centre, `[0, 0]` bottom-left |
| `layer`, `order` | stacking: `layer` first (−100..100), then `order` within the layer, then ECS order |
| `flip_x`, `flip_y` | mirror |
| `region` | the part of the texture shown, `[u0, v0, u1, v1]` from 0 to 1 with `v0` the top edge; `[0, 0, 1, 1]` (the default) is the whole texture |

`region` picks a frame out of an atlas by hand; an `AnimatedSprite` (7.3) writes it for you.
Missing or broken textures draw as a magenta checker rather than nothing.

Sprites are point-sampled by default, which keeps pixel art crisp. For smooth, painted or
vector-like art that gets magnified (HiDPI screens, phones, full-screen overlays), import the
texture with `"filter": "linear"` in its sidecar (chapter 5); every kit sprite drawing that
texture then samples it bilinearly. Tilemap layers stay point-sampled.

**Colour spaces.** Sprite `tint`, `TextLabel.color`, `Light2D.color` and particle colours are
**linear** RGB: the batch encodes them to sRGB for the screen. A colour picked from a design
palette (sRGB, like a hex code) comes out lighter unless you convert it first, channel by
channel, with about `c^2.2` (`#1A2130` = `[0.10, 0.13, 0.19]` in sRGB is `[0.006, 0.011, 0.026]`
linear). The camera's `clear_color` is the exception: it is written to the screen as it is, so
it takes the sRGB value directly.

## 7.2 The camera

`Camera2DComponent` on an entity makes that entity's position and Z rotation the view:

| Field | Meaning |
|---|---|
| `pixels_per_meter` | 48 by default: a 1280 x 720 window shows about 26.7 x 15 m |
| `zoom` | 1 = one texel per pixel at `pixels_per_meter` |
| `clear_color` | the background, in **sRGB** as written (unlike tints, which are linear; see 7.1) |
| `primary` | the first primary camera in ECS order is the one rendered |
| `pixel_snap` | snap the view to whole pixels so pixel art stays crisp |
| `fit_width`, `fit_height` | fit mode: > 0 shows at least that many metres across / up on every screen (both set: the whole rect, the longer axis shows more); overrides `zoom` and its pixel-snap quantization; 0 = off |

On phones, use fit mode: without it the visible area follows the pixel count, so a 2400 x 1080
phone sees about 1.9 times the world a 1280 x 720 window does. `fit_height = 15` shows 15 m up on
any screen; wider screens show more width. Check layouts at phone sizes on desktop with
`-window 1080x2400` (chapter 16).

The player writes a `kit::ViewInfo` world resource before every tick: framebuffer size in
pixels, window size in points, display scale, safe-area insets, orientation, and the primary
camera's resolved view. `world.try_resource<kit::ViewInfo>()` reads it; its `touch_to_world`,
`mouse_to_world` and `screen_to_world` map `InputState::touch_points()`, `mouse_pos_px()` and
pixels to world metres. Headless runs write a fixed 1280 x 720 landscape screen so state hashes
stay deterministic; a game that reads it in windowed runs simulates differently per window size.

`CameraFollow2D` on the camera entity follows another entity in `FixedUpdate_Post`:

| Field | Meaning |
|---|---|
| `target` | the entity to follow (the first tick starts on it) |
| `offset` | from the target to the view centre |
| `dead_zone` | half-size in metres the target moves before the camera does |
| `smoothing` | 1/s easing toward the goal; 0 snaps every tick |
| `look_ahead` | seconds of the target's velocity to lead by |
| `use_bounds`, `bounds_min`, `bounds_max` | keep the view centre inside the level |

`CameraShake2D` on the camera adds trauma shake (the `render::ScreenShake` model): `trauma` 0..1
decays by `decay_per_second`, and the view moves by up to `max_translation` metres and turns by
`max_rotation` radians times trauma². The noise comes from `seed` and the tick time, so replays
shake the same. `ShakeTrigger {trauma}` elsewhere adds trauma to every `CameraShake2D`; its `on`
works as for the other triggers (7.9).

## 7.3 Animation

A **sprite sheet** (`.mcsheet`, a JSON source like the other kit assets; MCP `asset_create` makes
one) cuts one texture into regions and names flipbook clips over them:

```json
{
  "format": "mce-spritesheet", "version": 1, "guid": "<uuid>", "name": "hero",
  "texture": "guid:<texture uuid>",
  "grid": { "columns": 8, "rows": 4, "count": 30 },
  "image_size": [256, 128],
  "regions": [ { "name": "hurt", "rect": [224, 96, 32, 32] } ],
  "clips": [
    { "name": "run", "frames": { "from": 0, "to": 7 }, "fps": 12,
      "events": [ { "frame": 2, "name": "footstep" }, { "frame": 6, "name": "footstep" } ] },
    { "name": "die", "frames": [24, 25, 26, "hurt"], "fps": 8, "mode": "Once" }
  ]
}
```

Regions are numbered: the `grid` cells first (left to right, top row first; `count` drops unused
cells at the end), then the `regions` pixel rects (`[x, y, width, height]`, y down from the top,
which need `image_size`). A clip's `frames` are region indices or names, or a `from`/`to` range
(backwards when `to` is smaller); `mode` is `Loop` (default), `PingPong` or `Once`; `events` fire
when playback enters that frame of the clip.

`AnimatedSprite` next to a `Sprite` plays it:

| Field | Meaning |
|---|---|
| `sheet` | the `.mcsheet` |
| `clip` | the clip to play; empty = the first. Changing it starts the new clip from its first frame |
| `speed` | playback rate; 0 holds the frame |
| `playing` | clear it to pause |
| `restart` | set it to play the clip again from the start (the engine clears it) |
| `finished`, `frame`, `time`, `last_event`, `events_fired` | read-only: where playback is |

Every fixed tick the stock systems (`"kit_sprite_animation"`, `FixedUpdate_Post`) step the clip,
never blending frames, and write the sheet's texture and the frame's `region` into the `Sprite`.
Frame events also arrive as `kit::SpriteAnimEvent {entity, id, frame}` (`id` is the low 32 bits of
`fnv1a64(name)`; `mce/kit/sprite_anim.h`), so a footstep sound or a hitbox can hang off them. A
game switches clips by writing `clip`, from code, a sequence's field track or MCP.

Without a sheet, animate by swapping the texture reference:

```cpp
void set_texture(kit::Sprite& s, const asset::AssetRef<asset::Texture>& tex) {
    if (tex.guid.is_null() || s.texture.guid == tex.guid) return;
    s.texture = asset::AssetRef<asset::Texture>{tex.guid, {}};
}
```

Keep the frame references as `AssetRef<Texture>` fields on your component (`idle`, `run_a`,
`run_b`, `jump`) so the editor sets them, and switch on a tick counter (`(ticks / 6) % 2` for a
two-frame run cycle at 10 fps). Resolved textures are cached per GUID, so swapping costs nothing
after the first draw.

### Importing from Aseprite

`mce import aseprite <export.json>` turns Aseprite's sprite-sheet export into a `.mcsheet`. In Aseprite,
File > Export Sprite Sheet, turn on **JSON Data** (array or hash frames) and **Tags**, and **Slices** if you
use them; leave Trim off. Then:

```
mce import aseprite assets/sprites/hero.json        # writes hero.mcsheet and, if missing, hero.png.mceasset
```

Every frame becomes a region (region index = frame index, in export order), every tag a clip (`forward`,
`reverse`, `pingpong`, `pingpong_reverse`; ping-pong plays in `PingPong` mode), every slice a named region
after the frames. A clip's fps is 1000 over its frames' mean duration. A file with no tags gets one clip,
`all`. The PNG gets a pixel-art texture sidecar (`filter: nearest`) when it has none. Importing again keeps
the sheet's GUID and gives the same bytes, so the converted `.mcsheet` can be committed and diffed.

Anything the converter cannot carry is a warning on stderr that names it: trimmed or rotated frames,
frame durations that differ inside one tag, a tag name over 31 characters or used twice, a slice that moves
over time. `--werror` makes warnings a failure and writes nothing; `--out` and `--name` change the file
written. The export JSON itself is not an asset: keep it outside `assets/`, or accept the cook's "no
importer for this file type" warning.

### Importing from Tiled

`mce import tiled <map.tmj>` turns a Tiled map into a scene and tilemaps. In Tiled, build an orthogonal,
finite map (Infinite off), embed its tilesets or save them as `.tsj`, and export it as JSON (`.tmj`).
Then:

```
mce import tiled assets/levels/cave.tmj --tile-size 1     # writes cave.mcscene, cave_<layer>.mctilemap
```

Each tile layer becomes one `.mctilemap` (one per tileset when a layer mixes tilesets) with its own
`TilemapLayer` entity in the scene, in layer order; rows are flipped to the engine's bottom-up order, layer
opacity becomes the tint, hidden layers are skipped. Collision comes from a layer property `collide = true`
or from tileset tiles with a bool property `solid = true`; neighbouring solid tiles merge into static boxes.
On an object layer a rectangle is a static `Collider2D` box (bool properties `sensor` and `one_way`) and a
point is a named marker entity to find from code. The tileset images get pixel-art texture sidecars. One
tile is one metre unless `--tile-size` says otherwise, and importing again keeps every GUID and gives the
same bytes.

Flipped or rotated tiles, animated tiles, rotated objects, ellipses, polygons, text and tile objects, and
image layers are warnings that name them (`--werror` makes them failures). Infinite, isometric and hex maps,
tileset margin or spacing, XML tilesets and a tileset image that is not the size Tiled records are errors
that say how to fix the map.

For cut-out characters built from parts on bones, see 2D skeletons (7.13).

## 7.4 Text

`TextLabel` draws world-space text from a cooked font asset: `font`, `text` (up to 63
characters), `color` (linear RGB, see 7.1), `height` in metres, `align` (left, centre, right about the entity's
position), `layer` and `order`. Your game writes `text` with `label.text.assign(StringView(buf))`.
`wrap_width` (metres, 0 = one line) breaks lines at spaces, each aligned by `align`. `loc_key`
shows that key's string in the player's language from the project's string tables
(`assets/loc/<locale>.csv`, chapter 21); without tables the label shows `text`.

A label's look is set in fractions of its `height`, so it scales with the text:

| Field | What it does |
|---|---|
| `letter_spacing` | extra space between letters (0.1 = a tenth of the height; negative tightens) |
| `line_height` | multiplies the font's line height for wrapped and multi-line text (1 = the font's own) |
| `outline_width`, `outline_color` | rings every glyph (0.06–0.1 reads well on busy backgrounds; 0 = none) |
| `shadow_offset`, `shadow_color` | a copy of the text under it, moved by the offset (+y up, so `[0.06, -0.06]` drops it down-right; `[0, 0]` = none) |

The outline is drawn as eight copies of the glyphs around the text, so keep it thin next to the
glyph strokes; a pixel font with an outline of one font pixel (`1 / size`) gives the classic look.

Fonts are `.ttf` files cooked into an atlas; the sidecar's `size` is the baked pixel height, so
pick one that matches the on-screen size you need (26 px works for HUD text at 48 px/m).

**Screen-space HUD.** There is no HUD component. Put a `TextLabel` on an entity with
`Parallax {"factor": [0, 0]}`: it then stays fixed to the camera. Author it at the offset from the
camera centre where it should sit (for the default view that is ±13.3 m by ±7.5 m) and give it a
high `layer`. Kindle's `HudText` component marks which label shows what, and one system writes
the strings.

## 7.5 Parallax and backdrops

`Parallax` on an entity scrolls its sprite, tilemap or text against the camera by `factor` per
axis: 1 moves with the world, 0.5 is a far background, 0 is pinned to the camera, above 1 is a
foreground. `repeat_x` tiles a sprite endlessly across the view. Author the layer where it sits
when the camera is at the origin. A `factor.y` of 0 pins a sky vertically, which suits a sideways
scroller.

## 7.6 Lighting

Sprites with a `normal_map` are lit by `Light2D` entities; everything else ignores lights.

- `Light2D {"kind": "Point", "color", "intensity", "radius", "height"}` at the entity's position;
  `color` is linear RGB (7.1).
  At most 16 point lights touching the view are used, in ECS order.
- `Light2D {"kind": "Ambient"}` sets the base light every lit sprite receives (white when the
  scene has none).

Import normal maps with `srgb: false`. The `extras_2d` sample shows a lit scene.

## 7.7 Post effects

`Post2DComponent` on the camera entity adds three effects, each toggled by its own flag (all
off by default): `vignette` (`vignette_intensity`, `vignette_radius`, `vignette_softness`),
`color_grade` through a 256 x 16 LUT strip (`lut`, imported with `srgb: false`;
`render::make_identity_lut` makes a neutral one to edit) with `lut_strength`, and
`chromatic_aberration` (`aberration`). F7 in the player toggles post
effects for comparison (`-r.post2d 0` starts with them off).

## 7.8 Tilemaps

A `TilemapLayer` draws one `.mctilemap` asset (`map`) with its tile (0, 0) at the entity's
position; `tint` colours it and `layer`, `order` stack it like a sprite. The
asset holds the tileset texture, the grid cell counts and the tile indices; the editor's Tilemap
panel creates and paints it:

1. Select an entity, open the Tilemap panel, choose a tileset texture and the grid (columns, rows,
   width, height, tile size).
2. Press T (or "Paint tiles" in the View menu). Pick a brush cell from the tileset. Left drag
   paints, Ctrl erases, Shift+drag fills a rectangle.
3. Every stroke saves the asset and hot-reloads it.

Limits today: one layer per asset, no auto-tiling and no palette thumbnails. An agent paints with
the MCP tool `tilemap_paint` (cells, rectangles and flood fills; chapter 14). A tilemap draws only;
give the ground a `Collider2D` on a separate entity (or several).

## 7.9 Particles

`ParticleEmitter` plays a `.mcpart` preset from the entity's position:

| Field | Meaning |
|---|---|
| `preset` | the `.mcpart` asset: texture, rate, lifetime, speed, direction and spread, gravity, drag, size and colour over life, blend mode |
| `seed` | per-emitter random stream (mixed with the entity index), so runs are reproducible |
| `playing` | emitting; clear it to stop while live particles finish |
| `destroy_when_done` | one-shots: destroy the entity when the last particle dies |
| `layer`, `order` | stacking like a sprite |

Particles are simulated on the fixed tick on the CPU and drawn as sprites in the same batch, so
they sort with sprites and cost one draw. From code, `f.resource<kit::ParticleSystem>().burst(e, n)`
emits `n` particles at once; without code, `ParticleBurst {count}` next to the emitter does.
`on` picks when it fires: `Manual` when its `fire` flag is set (by data, a sequence field track or MCP `entity_set_component`; the engine clears it), `Start` on the first tick, `TriggerEnter` / `ContactBegin` when a 2D physics event names the entity (as the sensor, the other body or either contact body), `Landed` when a 3D character on the entity touches down, `Skid` when a wheel of the entity's `Vehicle3D` starts to skid, `Lap` when the entity's `VehicleDriver3D` completes a lap. `fired` counts the plays.

## 7.10 Pathfinding

Enemies that chase the player around walls, units sent to a tapped point and tower-defense creeps
walk with a `PathAgent` over a walkability grid. The grid is a `kit::NavGrid` world resource. The
stock systems build it at the first tick: from the first `NavGridSource` in the scene (a
`tilemap` layer entity, one cell per tile with non-empty tiles blocked, or else a `width` x `height`
grid of `cell_size` cells at `origin`; with `colliders`, static colliders grown by `inflate` block
cells too; set `rebuild` to build it again), or, with none, from the static colliders over the
area of the agents and their targets (half-metre cells, 4 m margin). So a `PathAgent` placed in
the editor or over MCP walks with no code. A game can also build it (and rebuild or edit it when
walls change): width x height square cells of
`cell_size` metres, cell (0, 0) bottom-left at `origin`, a cost per cell where 0 is blocked, 1 is
normal and up to 255 is slow terrain the search avoids when it can.

```cpp
#include "mce/kit/pathfinding.h"

// From the level's tile layer: one cell per tile, every non-empty tile a wall.
auto map = asset::TilemapView::read(assets.resolve(tilemap_handle)).value();
kit::NavGrid grid = kit::nav_grid_from_tilemap(map, layer_position);
// Or only some tiles are walls, the rest floor:
//   const u32 walls[] = {3, 4, 9};
//   kit::nav_grid_from_tilemap(map, layer_position, Span<const u32>(walls, 3));
kit::mark_static_colliders(grid, world, /*inflate=*/0.25f);  // static Collider2D bodies too
grid.set_cost(grid.cell_at({4.0f, 2.0f}), 5);                // a patch of mud
kit::install_path_agents(world, static_cast<kit::NavGrid&&>(grid));
```

`mark_static_colliders` blocks every cell under a static body's collider (its bounding box, grown
by `inflate` so agents keep that far from walls); sensors and one-way platforms are ignored. A
tilemap and the grid line up when the grid's `origin` is the `TilemapLayer` entity's position.

`PathAgent` fields:

| Field | Meaning |
|---|---|
| `target` | world point to walk to; changing it re-plans on the next tick |
| `speed` | metres per second |
| `arrival_radius` | how close to `target` counts as arrived |
| `repath_interval` | ticks between re-plans while moving or blocked (walls that moved are seen then); 0 re-plans only when the target changes |
| `active` | clear it to stop the agent where it is |
| `diagonal` | 8-neighbour paths (default); cleared, 4-neighbour |
| `status` | read-only: `Idle`, `Moving`, `Arrived` or `NoPath` (target blocked or walled in) |

The `"path_agents"` system runs in `FixedUpdate_Pre`. An entity with a physics body (chapter 9) is
driven through its velocity, so it still collides; give a dynamic one `gravity_scale` 0 in a
top-down game. Other entities move their `LocalTransform` directly. A tap-to-move game sets
`target` from `world.resource<kit::ViewInfo>().touch_to_world(...)`.

For your own queries, `kit::Pathfinder` returns cell paths (`find_cells`) or world waypoints
(`find_path`, smoothed by default) and keeps its scratch between calls, so one planner per system
avoids allocation. Paths never squeeze diagonally past a wall corner, and smoothing pulls them
taut only through cells as cheap as the ones it skips. The search uses integer costs with a fixed
tie-break, so the same grid and endpoints give the same path on every machine and replays keep
their hashes.

`kit::debug_draw_grid` and `kit::debug_draw_agents` emit the blocked cells and the agents' paths as
lines into a `physics::DebugDrawSink`; the editor viewport does not show them yet.

## 7.11 Stacking and sorting

Draw order is `layer`, then `order`, then ECS order (deterministic). Text draws above its layer's
quads. UI documents (chapter 12) draw on top of everything in screen space.

## 7.12 What the kit does not do

The kit draws, animates sprites, follows, shakes and plays effects; gameplay is yours. There is no player
controller, pickup, hazard, goal or moving platform component in the engine. Ember Step's versions (`samples/03_platformer/
game/`) are spawned from code; Kindle's (`projects/Kindle/games/kindle/module/components.h`) are
reflected components a scene authors, and they are the recommended starting point: copy
`PlayerController`, `Coin`, `Hazard`, `Goal`, `Crumble`, `Mover`, `CameraFollow` and `HudText` with
their systems into your module and change what you need.

## 7.13 2D skeletons

A **2D skeleton** (`.mcskel2d`, a JSON source; MCP `asset_create` makes one) is a cut-out character:
a tree of bones and the textured quads (slots) that ride them. Move a bone and every slot on it and
on its children moves with it. The skeleton also holds its animations (clips of bone keys), which a
`Skeleton2DAnimator` plays and cross-fades, optionally under an animation graph. A slot can also
hold several attachments, show one at a time, and draw a skinned mesh. IK constraints turn limbs
onto targets. You do not have to write the text by hand: see Editing at the end of this section.
`samples/skel2d_demo` puts all of it in one scene (the last subsection).

```json
{
  "format": "mce-skeleton2d", "version": 1, "guid": "<uuid>", "name": "hero",
  "bones": [
    { "name": "root" },
    { "name": "torso", "parent": "root", "y": 0.5, "length": 0.6 },
    { "name": "arm", "parent": "torso", "x": 0.15, "y": 0.5, "rotation": -30, "length": 0.4 }
  ],
  "slots": [
    { "name": "body", "bone": "torso", "texture": "guid:<texture uuid>", "rect": [0, 0, 0.5, 1],
      "size": [0.4, 0.7], "pivot": [0.5, 0] },
    { "name": "arm", "bone": "arm", "texture": "guid:<texture uuid>", "rect": [0.5, 0, 1, 0.5],
      "size": [0.4, 0.12], "pivot": [0, 0.5], "tint": [1, 1, 1, 1] }
  ]
}
```

Bones:

| Field | Meaning |
|---|---|
| `name` | 1 to 31 characters, unique in the skeleton |
| `parent` | a bone listed earlier; absent for a root. The first bone is a root |
| `x`, `y` | the rest position in the parent's space, metres |
| `rotation` | the rest rotation, degrees counter-clockwise |
| `scale` | `[sx, sy]` or one number; default 1 |
| `length` | metres along the bone's +x; for gizmos and IK later |

List parents before their children. The cook stops on a bone whose parent comes later and names
both bones. A skeleton has at most 64 bones and 256 slots.

Slots draw in the order listed: the first is drawn first, behind the rest. Each slot is a quad like
a `Sprite`: `texture` (null or absent draws a solid quad in `tint`), `rect` (`[u0, v0, u1, v1]`, v0 at
the top), `size` in metres and `pivot` (0 to 1, `[0, 0]` bottom-left). `offset` (metres) and
`rotation` (degrees) place the pivot in the bone's space. Slot names are unique too.

A `Skeleton2D` component draws a skeleton on its entity:

| Field | Meaning |
|---|---|
| `skeleton` | the `.mcskel2d` |
| `tint` | multiplies every slot's tint |
| `layer`, `order` | sorting, as on `Sprite` (7.11) |
| `flip_x`, `flip_y` | mirror the whole skeleton about the entity's origin |
| `visible` | clear it to hide the slots |
| `pose` | one entry per bone: an offset from the rest pose. `x`, `y` and `rotation` (radians) add, `scale_x` and `scale_y` multiply |
| `bone_count`, `world` | read-only: the bones the last tick posed, each as a 2D transform in the skeleton's space |

Every fixed tick the stock systems (`"kit_skeleton2d"`, `FixedUpdate_Post`) combine the rest pose with
`pose` and compute each bone's transform: the parent's transform times the bone's translate, rotate
and scale. A parent's scale reaches its children, as in Spine and Godot. The pose lives in the
component, so it is in the state hash, in replays and in saves (`pose` carries the `Save` flag).

Animate a bone by writing its `pose` entry: from code (`sk.pose[2].rotation = angle;`), from a
timeline property track (`"path": "Skeleton2D.pose[2].rotation"`) or from MCP (`component_set` with
`"path": "pose[2].rotation"`). In a `.mcscene` `pose` is an array of all 64 entries, and `{}` keeps a
bone at rest. The editor and MCP write the whole array for you.

`Bone2DFollow` keeps another entity on a bone: a sword in a hand, a muzzle flash on a gun.

| Field | Meaning |
|---|---|
| `skeleton` | the entity with the `Skeleton2D` |
| `bone` | the bone's name |
| `offset`, `rotation` | where on the bone, in the bone's space (metres, radians) |
| `follow_rotation`, `follow_scale` | take the bone's rotation (default on) and scale (default off) |

The follower's `LocalTransform` is written each tick. When the follower is a child (`ChildOf`) of the
skeleton's entity it gets the bone in the skeleton's space, otherwise in the world. Its z is kept.
From code, `kit::skeleton2d_bone(world, entity, "hand", out)` reads a bone's transform.

Drawing goes through the same batch as sprites, so lights, sorting and post effects apply. Two
limits come from the 2D batch. Within one layer it groups quads by texture before `order`, so slots
draw in exact slot order only when they share one texture: put a character's parts in one atlas.
And a quad cannot shear: a slot on a rotated bone under a non-uniformly scaled parent keeps its
axis lengths but loses the shear.

### Animations

A skeleton's `"animations"` are named clips. Each clip keys bones over time and can raise events:

```json
"animations": [
  { "name": "walk", "duration": 1, "loop": true,
    "bones": {
      "arm": {
        "rotate": [ { "t": 0, "value": -20 }, { "t": 0.5, "value": 20, "curve": [0.25, 0, 0.75, 1] },
                    { "t": 1, "value": -20 } ],
        "translate": [ { "t": 0, "x": 0, "y": 0 }, { "t": 0.5, "y": 0.05, "curve": "stepped" } ],
        "scale": [ { "t": 0, "x": 1, "y": 1 } ] } },
    "events": [ { "t": 0.5, "name": "step" } ] }
]
```

| Field | Meaning |
|---|---|
| `name` | 1 to 31 characters, unique in the skeleton |
| `duration` | seconds; default: the last key or event |
| `loop` | default true; false plays the clip once and holds its last pose |
| `bones` | per bone name: `rotate`, `translate` and `scale` key lists |
| `events` | `{ "t", "name" }` in time order; names are 1 to 23 characters |

Keys are offsets from the rest pose, like `Skeleton2D.pose` (Spine works the same way). `rotate`
`value` is degrees added to the bone's rotation. `translate` `x`, `y` are metres added (default 0).
`scale` `x`, `y` multiply the rest scale (default 1). List keys in increasing `t`. A key's `curve`
shapes the interval up to the next key: `"linear"` (the default), `"stepped"` (hold the value) or a
cubic bezier `[cx1, cy1, cx2, cy2]` in the key interval scaled to 0..1, with `cx1` and `cx2` in 0..1.
The bezier is solved with a fixed number of steps, so it gives the same bits on every machine.
Before the first key a channel holds the first value, after the last key the last value.

Cook errors name the file position, the animation and the bone, for example
`animation 'walk', bone 'arm': rotate keys must be in increasing time order`.

### Playing animations

Put a `Skeleton2DAnimator` next to the `Skeleton2D`. It works like the 3D `Animator` (8.9).

| Field | Meaning |
|---|---|
| `clip` | the animation to play; a new name starts it at 0 and cross-fades from the old one |
| `speed` | playback rate (default 1) |
| `fade` | cross-fade seconds (default 0.2; 0 cuts) |
| `time` | seconds into `clip`; the engine advances it, a game may set it |
| `loop` | default on; off plays even a looping clip once |
| `restart` | set it to play the clip again from 0; the engine clears it |
| `graph`, `params` | an animation graph and its parameters (below) |
| `state`, `finished`, `playing`, `previous`, `previous_time`, `blend`, `blend_clip`, `blend_weight`, `last_event`, `events_fired` | read-only runtime state |

A clip loops when its `loop` and the animator's `loop` are both on. Otherwise it plays once, holds
its last pose and sets `finished`.

The stock system `"kit_skeleton2d_animators"` runs in `FixedUpdate_Post` just before
`"kit_skeleton2d"`. Each tick it advances the playhead, samples the clip and the clip fading out,
blends them by `blend` and writes the result into `Skeleton2D.pose`. It writes only the channels the
sampled clips key. A channel is one bone's rotation, translation or scale. A channel that no clip
keys keeps what gameplay or a timeline wrote, so code can aim an arm while a clip walks the legs.
During a cross-fade, a clip that does not key a channel the other clip keys counts as the rest
pose for it. Rotations blend linearly as offsets, so keep a cross-fade's rotations within half a
turn of each other.

Every animator field is in the state hash and carries the `Save` flag: a save made in the middle of
a cross-fade resumes exactly.

### Animation graphs

Set `graph` to an `.mcanim` animation graph (8.9) to drive the animator with states and
transitions. A state's `clip` names one of the skeleton's animations; clip lengths come from the
skeleton. Everything the 3D state machine does works here: `params` (up to 4 values in the graph's
order), transitions on parameter conditions or when a one-shot state finishes, each with its own
fade, `"*"` transitions, 1D and 2D blend states, state speed and loop, state events and `restart`.
The graph step is the same code the 3D `Animator` runs. A graph's layers, root motion and IK chains
are 3D only and are ignored on a 2D skeleton.

### Events

A clip's events, and a graph state's events, raise `kit::AnimEvent3D` (`mce/kit/anim3d.h`), the event
the 3D `Animator` raises. It carries the entity and the event name's `StringId`. An event fires once
each time the playhead crosses it, a loop wrap crosses it again, and a one-shot's event at its end
fires when the clip finishes. Read them in `FixedUpdate_Pre` of the next tick or later:

```cpp
for (const kit::AnimEvent3D& ev : f.events().read<kit::AnimEvent3D>())
    if (ev.id == StringId("step").value) play_footstep(ev.entity);
```

`last_event` and `events_fired` on the animator show the latest one in the inspector.

### Attachments

A slot shows one **attachment** at a time. The slot fields above make one quad attachment named
after the slot, so a step-1 skeleton reads and draws as before. To give a slot several, list them:

```json
{ "name": "hand", "bone": "arm", "tint": [1, 1, 1, 1], "attachment": "open",
  "attachments": [
    { "name": "open", "texture": "guid:<texture uuid>", "rect": [0, 0, 0.5, 0.5], "size": [0.2, 0.2] },
    { "name": "fist", "texture": "guid:<texture uuid>", "rect": [0.5, 0, 1, 0.5], "size": [0.2, 0.2] },
    { "name": "cape", "type": "mesh", "texture": "guid:<texture uuid>",
      "vertices": [
        { "uv": [0, 0], "x": -0.2, "y": 0.6 },
        { "uv": [1, 0], "x": 0.2, "y": 0.6 },
        { "uv": [1, 1], "weights": [ { "bone": "arm", "x": 0.25, "y": 0, "weight": 0.5 },
                                     { "bone": "torso", "x": 0.25, "y": 0.5, "weight": 0.5 } ] },
        { "uv": [0, 1], "weights": [ { "bone": "arm", "x": -0.25, "y": 0, "weight": 1 } ] } ],
      "triangles": [0, 1, 2, 0, 2, 3] } ] }
```

| Field | Meaning |
|---|---|
| `attachments` | 1 to 64 attachments; names are unique within the slot |
| `attachment` | the one shown at first; default the first listed; `null` hides the slot |
| `type` | `"quad"` (the default) or `"mesh"` |
| quad fields | `texture`, `rect`, `size`, `pivot`, `offset`, `rotation`, as on a slot |
| `vertices` | a mesh's 3 to 1024 vertices, each with `uv` (0 to 1, v = 0 at the top) |
| `triangles` | vertex indices, three per triangle, 1 to 2048 triangles |

A slot that lists `attachments` takes no quad fields itself; its `tint` is still the slot color.

### Meshes and skinning

A mesh vertex either sits in the slot bone's space (`x`, `y` in metres) or is **weighted** to 1 to 4
bones. Each weight gives a bone, a position in that bone's space and a weight. The vertex lands on
the weighted sum: weight times the bone's world transform times the position, the same as Spine's
weighted meshes. The cook divides the weights by their sum, so they add up to 1. A vertex weighted
half to an upper arm and half to a forearm bends smoothly at the elbow.

Skinning runs on the CPU in a fixed order, with no fused multiply-adds, so it gives the same bits on
every machine. Meshes go through the same 2D batch as sprites (as triangles), on the skeleton's
`layer` and `order`, so lights and sorting apply. On a lit texture (a normal map) a mesh turns its
normals by its slot bone's angle. A mesh can shear, unlike a quad.

Limits: 64 attachments per slot and 4096 per skeleton, 65536 mesh vertices, 262144 weights and
393216 triangle indices in all.

### Slot and deform keys

An animation can key slots and meshes as well as bones:

```json
{ "name": "punch",
  "slots": { "hand": { "attachment": [ { "t": 0, "name": "fist" }, { "t": 0.4, "name": "open" } ],
                       "color": [ { "t": 0, "color": [1, 1, 1, 1] }, { "t": 0.2, "color": [1, 0.5, 0.5, 1] } ] } },
  "deform": { "hand": { "cape": [ { "t": 0 }, { "t": 0.5, "offsets": [0, 0, 0, 0, 0.05, 0, 0.05, 0] } ] } } }
```

| Key list | Meaning |
|---|---|
| `color` | the slot color, absolute linear RGBA (not an offset). Alpha 0 hides the slot |
| `attachment` | the attachment shown from `t` on; `null` hides the slot. Always stepped |
| `deform` | per mesh attachment: `offsets`, an x and y per vertex (default 0), added to the vertex's positions |

Color and deform keys take a `curve` like bone keys. A deform offset is in the space of the bones
the vertex follows, so it turns with them.

In a cross-fade, colors and deform offsets blend by weight like bone channels. A clip that does not
key a slot's color counts as the slot's own tint; one that does not key a mesh counts as no offset.
Attachments do not blend: the incoming clip decides as soon as it has any weight, which is the
tick after the switch. If only the outgoing clip keys a slot's attachment, it keeps deciding until
the fade ends.

### Slot state

The attachment each slot shows and its color live in an optional `Skeleton2DSlots` component next
to the `Skeleton2D`:

| Field | Meaning |
|---|---|
| `attachment` | per slot: the index of the attachment shown in the slot's list; 255 hides the slot |
| `color` | per slot: linear RGBA, times the `Skeleton2D` tint |
| `slot_count` | read-only: the slots it was set up for (0: not yet) |

The animator adds it on the first tick when the skeleton's clips key slots. Without it every slot
shows its first attachment and its tint. Add it yourself to swap attachments from code: the next
tick fills it from the skeleton, then write `attachment[i]` (`kit::Skeleton2DRegistry::Def::find_attachment`
finds an index by name). The animator writes only the slots its clips key, so code owns the rest.
The component is 4.3 KB, saved and hashed.

Deform offsets are not stored. The extract samples them from the clips each frame. They depend
only on the animator's saved fields, so replays and loaded saves draw the same offsets.

### IK

IK constraints turn a chain of bones so its tip reaches a target. They live in the skeleton's
`"ik"` list:

```json
"ik": [
  { "name": "arm", "bones": ["upper_arm", "forearm"], "target": "hand_goal", "bend": "negative" },
  { "name": "tail", "bones": ["tail1", "tail2", "tail3"], "target": "tail_goal", "iterations": 12 },
  { "name": "look", "bones": ["head"], "order": -1 } ]
```

| Key | Meaning |
|---|---|
| `name` | 1 to 31 characters, unique |
| `bones` | the chain, parent first: each bone is the child of the one before. 1 to 32 bones |
| `target` | a bone the tip reaches. It must be outside the chain and not under its first bone. Leave it out (or `null`) when only an entity drives the constraint |
| `type` | `"two_bone"` (the default for two bones) or `"ccd"` (the default otherwise) |
| `bend` | two-bone only: `"positive"` (default) bends the elbow counter-clockwise, `"negative"` clockwise |
| `iterations` | CCD only: 1 to 64 passes, default 10 |
| `mix` | 0 to 1, default 1: how far the solve moves the chain from its pose |
| `order` | constraints apply in this order, default 0. Ties keep the listed order |

At most 16 constraints. `"kit_skeleton2d"` applies them every tick after the pose (clips and
gameplay writes) and before it writes `world`, so `Bone2DFollow` followers and the drawn slots see
the solved bones. IK never writes `pose`: turn it off and the clip's pose is back.

How each kind solves:

- Two-bone uses the law of cosines, so the tip lands on a reachable target exactly. A target out
  of reach gets the arm pointing straight at it. Bone lengths never stretch. The solve is exact
  for bones without non-uniform scale; with it the tip lands close.
- CCD turns each bone of the chain in turn, tip first, toward the target, for exactly
  `iterations` passes. There is no "close enough" exit, so every run gives the same bits.
- A chain of one bone simply aims it. A bone's tip is `length` along its +x; a bone of length 0
  aims its +x axis.

`mix` moves each rotation that fraction of the shortest way from its pose to its solve.

**Entity targets.** Put an `IKTarget2D` on any entity to make it a constraint's target in place
of its target bone: an arm aiming at the mouse cursor entity, a foot on a raycast hit point.

| Field | Meaning |
|---|---|
| `skeleton` | the entity with the `Skeleton2D` |
| `constraint` | the constraint's name |
| `mix` | 0 to 1, multiplies the constraint's mix |
| `enabled` | off: the constraint uses its target bone again (or keeps its pose without one) |
| `found` | read-only: 1 while the constraint resolves |

The entity's position is taken into the skeleton's space, with the skeleton entity's position,
rotation, scale and flips undone. An `IKTarget2D` that is a `ChildOf` the skeleton's entity is
already in its space.

**Keyed mix.** An animation can key a constraint's mix, with the usual curves:

```json
{ "name": "grab", "ik": { "arm": [ { "t": 0, "mix": 0 }, { "t": 0.3, "mix": 1 } ] } }
```

In a cross-fade the mix blends by weight like a slot color. A clip that does not key it counts as
the constraint's own `mix`.

**Mix state.** The mix in use lives in an optional `Skeleton2DIK` component next to the
`Skeleton2D` (132 bytes, saved and hashed):

| Field | Meaning |
|---|---|
| `mix` | per constraint, in the asset's order (sorted by `order`): the mix in use |
| `override_mix` | per constraint: a value from 0 to 1 replaces `mix`, keys included; negative (the default) leaves `mix` in use |
| `constraint_count` | read-only: the constraints it was set up for (0: not yet) |

The animator adds it when the clips key a mix. Add it yourself to turn constraints on and off from
code: write `override_mix[i]`, and `kit::Skeleton2DRegistry::Def::find_ik` gives `i` by name.
Without the component every constraint uses its asset `mix`. The limit is 16 constraints.

The sprite extract poses through the same `kit::skeleton2d_solve_pose` as the tick, with the same
targets and mixes, so an editor scene that has not ticked yet draws the solved pose too.

### The demo: `samples/skel2d_demo`

A data-only project the stock player runs: `mce_player -pack build/<preset>/samples/skel2d_demo/project/assets.mce`.
Its courier is a good template for a first rig.

| Piece | Where | What it shows |
|---|---|---|
| `skeletons/courier.mcskel2d` | 15 bones, 13 slots, all on `textures/courier.png` | the torso bone points up (`rotation` 90), so the torso and head slots turn by `-90` to stand upright; arms and legs are `[length, width]` quads along their bone with the pivot at the joint. One atlas keeps the slots in exact draw order |
| the cape | a mesh slot, 6 vertices, the lower four weighted to a `cape` bone | weighted skinning and a `deform` key list that flutters the hem, on top of the bone's own sway |
| the face | a slot with a `calm` and a `wow` attachment | the jump clip keys `wow` from take-off to just before landing; the idle and walk clips key `calm`, so the face is right after any cross-fade |
| `ik` | `leg_near` and `leg_far`, two-bone, `bend: negative` | knees forward. Idle has no IK keys, so the mix stays 1 and the feet hold their `IKTarget2D` while the hip breathes up and down. The walk and jump clips key the mix to 0 so the legs are pure keyed motion; the jump ramps it back to 1 as it lands |

`FootNear` and `FootFar` are `ChildOf` the courier, so their positions are already in its space
(0.14 m ahead and 0.14 m behind its root). The scene also names `Skeleton2DSlots` and `Skeleton2DIK`
with no fields so a reader sees where the state lives; the systems fill them from the skeleton.

The art is made by `samples/skel2d_demo/gen_art.py` (Pillow), so there is nothing to license.
`ctest -R skel2d_demo` plays the pack headless twice for one state hash, and the `test_kit` case
`skel2d_demo:` checks the poses: feet on their targets while idle and after the jump, the IK mix 0

### Editing

You can rig and animate a skeleton without writing the `.mcskel2d` text. A person uses the Skeleton
panel, an agent uses the MCP `skel2d_*` tools. Both change the same text through the same code, and
both cook the result with the real importer before keeping it. A bad edit is refused with the
importer's `file:line:col` message and the file stays as it was.

**The Skeleton panel.** Double-click a `.mcskel2d` in Assets (or open the Skeleton panel from the
View menu and pick one). The left side shows the tree of bones, the slots and the IK constraints.
Select a bone to edit its rest pose on the right: x, y, rotation in degrees and scale. The panel also
shows the bone's world transform. Pick an animation and drag the time slider (or press Play) to
preview the pose. Tick an IK constraint to aim it at a point you drag. With an animation chosen, set
a rotate, move or scale offset and press Key to write a key for the selected bone at the current
time. Add bone, Add slot and New animation make new entries. Undo and Redo work, and edits save by
themselves once you let go of a field.

In the 2D viewport, a selected entity whose `Skeleton2D` plays the open skeleton shows its bones as
lines: cyan for each bone, orange for the selected one. They follow the pose you chose in the panel.
The scene's sprites still show the saved pose, so the two can differ while you scrub. Bones cannot be
dragged in the viewport yet; use the fields.

**MCP.** An agent builds a rig in a few calls:

```
skel2d_create   {"path": "rigs/hero.mcskel2d"}
skel2d_add_bone {"skeleton": "rigs/hero.mcskel2d", "name": "arm", "parent": "root", "x": 0.2, "y": 0.8, "length": 0.4}
skel2d_add_slot {"skeleton": "rigs/hero.mcskel2d", "name": "arm", "bone": "arm", "texture": "guid:<uuid>", "size": [0.4, 0.12], "pivot": [0, 0.5]}
skel2d_key      {"skeleton": "rigs/hero.mcskel2d", "animation": "wave", "channel": "rotate", "target": "arm",
                 "keys": [{"t": 0, "value": -20}, {"t": 0.5, "value": 20, "curve": [0.25, 0, 0.75, 1]}, {"t": 1, "value": -20}]}
skel2d_preview  {"skeleton": "rigs/hero.mcskel2d", "animation": "wave", "time": 0.5}
```

`skel2d_preview` returns every bone's world transform, computed by the runtime's own pose functions
(`skeleton2d_pose_offsets`, the animator's blend and `skeleton2d_solve_pose`), so the numbers match
the game. `ik_targets` aims a constraint at a point, as an `IKTarget2D` entity would. The image is a
line drawing of the bones and slot quads, not the textures; render a scene with the skeleton in it
to see those.
