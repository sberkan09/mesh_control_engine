# Mesh Control Engine — Roadmap

**Project:** Mesh Control Engine (MCE) · **Document class:** Roadmap / plan
**Date:** 2026-10-06 · **Last revised:** 2026-10-13 (M-VISUAL added) · **Status:** AUTHORITATIVE sequencing for the tiers defined in `REQUIREMENTS.md` §6. Dependency-ordered; **every milestone ends in a running, demonstrable build** (the invariant from REQUIREMENTS §7.4). Sizes are relative (S ≈ 2–4 wk, M ≈ 4–8 wk, L ≈ 8–14 wk, XL ≈ 14–22 wk at the 10–15 h/wk baseline; velocity re-checked per NFR-B-07 — **cut feature scope, never the gate, never the demo**). Every milestone also carries an **effort estimate in hours** (engineering + content production, published next to the size); the tier bands in §2's tier map are the *sums* of those estimates — if a milestone's actual hours exceed its estimate by > 50 %, the named overrun-absorber milestone cuts per the ladder (see the tier map note).

Milestone naming note: the FR tables in REQUIREMENTS carry indicative M0–M5 tags; this document is the sequencing authority and maps to *tiers* (MVP / v0.5 / v1.0), not to those tags.

### M4.5 — Editor MCP server (AI-native tooling) · **size S (≈ 35–60 h engineering)** · tier: off-tier tooling (between the MVP gate and v0.5)

*Added 2026-10-08. Sequenced after the editor catch-up (the M2–M4 editor items — SceneDocument + EditorScene funnel, inspector, CRUD, cook panel, headless player — finished after the M4 gate) and before M5a. Design: `docs/architecture/editor-mcp.md`.*

**Builds:** `mce_mcp` — a headless Model Context Protocol server (JSON-RPC 2.0 over **stdio only**, no socket — N7 intact) linking `mce_editor_core` + `mce_engine`, never ImGui · `mce_mcp_core` (protocol, tool table, editor-side JSON codec — hand-written by default, ADR-0027 records the pick; the runtime stays JSON-free per FR-AST-010) · MVP tool table: discover (`refl_list_components`/`refl_describe_component` straight from `mce_refl`), read (scene, entities, components, GUID-registry assets), edit (entity create/delete/duplicate, component add/remove/set by refl property path — **every write goes through the `EditorScene` command funnel**, the same funnel as the inspector), persist (`scene_open`/`scene_save`), build (`cook_run`/`cook_errors`), verify (`run_headless`: N fixed ticks → `state_hash` + `World::metrics` + log tail), console (`console_list`/`console_exec`, cheats refused by default) · resources `mce://scene/current`, `mce://log`, `mce://refl/schema` · a checked-in `.mcp.json` so Claude Code can use it from a clone. **Stretch, cut in this order:** attach-to-running-editor (same tool table over a local pipe, edits visible live) first, then `render_frame` (offscreen PNG as MCP image content).

**Demo (running):** from a fresh clone, an MCP client connected to `mce_mcp --project samples/03_platformer` adds a pickup to the level through the tools, saves, cooks, calls `run_headless` for 300 ticks and gets a hash back; the same edit done through C++ `SceneCommand`s gives a byte-identical `.mcscene` and the same hash.
**Gates:** FR-EDT-160 acceptance · scripted MCP transcript test (initialize → tools/list → calls → shutdown, golden responses) · JSON codec fuzz target ASan-clean · walls: no ImGui and no socket symbols in `mce_mcp*`, no JSON codec linked into any runtime target · all of it inside `scripts/ci/local_ci.sh`.
**Overrun rule:** carries **no Must FRs**; like M3.5 it may slip whole (past M5b) without gating anything. In-game AI (LLM NPCs, runtime generation) is explicitly **not** this milestone — it is listed under M10+.

### M-VISUAL — High-end 3D rendering · **size XL (rough guess, ≈ 250–400 h engineering, not estimated per step)** · tier: off-tier renderer track, gates nothing

*Added 2026-10-13 by the user's request, after an assessment of the 3D path against current high-end rendering. ### M-UI-DATA — Data-driven game UI for SDK and MCP projects · **size L (rough guess, ≈ 90–150 h engineering, not estimated per step)** · tier: off-tier, opt-in, gates nothing

*Added 2026-10-14 by the user's request, after asking why every MCP-built game's UI looks alike. The cause is the engine more than the agents: `mce_ui` (panels, buttons, sliders, grids, scroll, tabs, modals, 9-slice, per-state styles) is reachable only from a C++ host, the stock player builds no documents, gameplay may not include `mce/ui`, and the MCP server has no UI tools (user guide 12.2). An MCP-authored game is left with `TextLabel` (font, color, height, align, 64 chars; no panel, outline, shadow or layout) and the template's one font, ProggyClean, which Kindle, PrismBreak, Undertow, SolsticeReach and Room3D all copied. Undelivered shows the engine can look different when a game brings its own fonts and painted sprites; this track makes that the easy path instead of the exception.*

**Builds, in order:** (1) UI documents as data: a `.mcui` asset (JSON source, cooked binary) describing a widget tree with anchors, stack/grid layouts, per-state styles, sprite regions with 9-slice and fonts by asset reference, round-tripping through the reflected `Ui*` types; the cook validates it · (2) the stock player loads documents: a `UiDocument` component (or a scene-level list) names which `.mcui` documents a scene shows (HUD, title, pause, win), the player builds them through `mce_ui`, draws them over the game and feeds them input; gameplay stays behind the UI wall by talking to documents only through data: read-only property bindings (`bind_property`) for HUD values, convar bindings for options, and UI events turned into gameplay events (a small `UiEvent` queue the module reads, recorded in replays) · (3) themes: a `.mcuitheme` asset (palette, fonts per role such as title, body and button, default widget styles, sprite set) that documents reference, so a game restyles every screen in one place; `apply_default_style` becomes the default theme · (4) text that carries a look: `TextLabel` and UI text gain outline, drop shadow, letter spacing and line height; the font pipeline handles larger sizes cleanly (SDF or multi-size atlases) and full Unicode ranges the localization tables need · (5) MCP tools: `ui_list`, `ui_create`, `ui_widget_add` / `ui_widget_set` / `ui_widget_remove`, `ui_theme_set`, `ui_preview` (a headless capture of a document at a given viewport and safe area), described through refl like the component tools · (6) the editor: a UI document panel (tree, inspector, live preview at phone and desktop aspect ratios) over the same assets · (7) the project templates ship two or three starter themes with different OFL fonts and sprite skins (for example pixel, clean sans, painted) instead of one font, and the MCP workflow guide (user guide 14) tells agents to pick or make a theme for each game.
**Demo:** an existing MCP-built game (Prism Break or Undertow) gets a title menu, an options screen with bound sliders, a pause modal and a HUD with a bar authored entirely through MCP calls and `.mcui` assets with no host code; two scenes of the same game rendered with two themes look clearly different; a fresh agent-built game in a blind test picks a non-default theme.
**Gates:** a `.mcui` round-trips through cook, editor and MCP unchanged; replay hashes hold with UI-raised gameplay events; the UI wall still holds (no gameplay module includes `mce/ui`); `ui_preview` captures are compared in tests; GL validation clean; `local_ci.sh` green on every step.

### M-DATA-REACH — Every engine feature reachable as data · **size L (rough guess, ≈ 110–180 h engineering, not estimated per step)** · tier: off-tier, gates nothing

*Added 2026-10-14 by the user's request, after the UI finding (M-UI-DATA) was checked against the rest of the engine. The same pattern holds almost everywhere: the MCP server is a generic component editor (`src/editor/mcp/src/tools.cpp`), so an agent, or a game on the stock player and template, reaches only what is a registered reflected component, a hand-written asset file or a console variable, while much of the engine is a C++ API, a world resource or an EventQueue event. The audit with file:line evidence is kept in the project's shared files (`assessments/motor-erisim-bosluklari.md`, 2026-10-14). Examples: `.mcmat` materials cook but the upload sink ignores them (`asset_upload.cpp`), `r.quality` is never called, there is no 2D sprite animation or atlas (`AnimatedSprite` is named in `render/sprite_animation.h` but never built), 3D physics has only static colliders built at Startup, one-shot SFX (`PlaySfx`), particle bursts and `render::ScreenShake` need code, the stock player never installs `PathAgent`'s system, MCP cannot create, open or instantiate prefabs (user guide 4 says it can), and `AudioSource` music is fully resident although user guide 10 says long clips stream.*

**Builds, in order:** (1) asset authoring over MCP: `asset_create` / `asset_write` / `asset_read` for every JSON source type (`.mcpart`, `.mcseq`, `.mctilemap`, `.mcmat`, `.mcinput`, `.mcstore`, `.mcconfig`, later `.mcui`) with a fresh GUID and sidecar, validated by the importer before the file is written, and their schemas served like `refl_describe_component`; `tilemap_paint` (cells, rects, fills) over the editor's tilemap code · (2) prefabs over MCP: `scene_open` / `scene_save` accept `.mcprefab`, `entity_create {"prefab": ...}` places an instance with overrides, `prefab_apply` / `prefab_create_from` (also an editor command: save selection as prefab); fix user guide 4 · (3) project settings: `project_get` / `project_set` for `.mceproj` (start scene, games, physics gravity, quality tier) and the scene `settings` object, with an editor Project Settings panel · (4) events and effects as components the stock player runs: `SfxTrigger` (one-shot, by bus enum, pitch range), `ParticleBurst` (count on a trigger field), `CameraShake2D` and `CameraFollow2D` / `CameraFollow3D` (target, dead zone, look-ahead, orbit), a `PhysicsEvents` component that records the last trigger/contact pairs so data and `run_headless inspect` can see them; the player installs `install_path_agents` and a `NavGrid` builds from colliders or a tilemap · (5) 2D animation: a sprite-sheet importer (grid or regions, named clips, frame events) and `AnimatedSprite` over `render/sprite_animation.h`; `Sprite.region` · (6) 3D bodies: `RigidBody3D` (dynamic/kinematic, sphere/capsule/box/convex), `CharacterController3D`, `Trigger3D`, poses written back to `LocalTransform`, colliders that follow moved or runtime-spawned entities · (7) animation control as data: one-shot clips with a finished flag, clip events into the event queue, `AttachToBone`, a small animation state graph asset (`.mcanim`: states, transitions on parameters, 1D blend) · (8) finish half-built features or correct the docs: `.mcmat` drives `MeshRef.material` (coordinate with M-VISUAL), music clips stream through `register_stream` with a crossfade, `r.quality` applies its tier, `AudioSource.bus` becomes an enum, `TextLabel` wraps and takes a loc key, novel components are registered in the stock `mce_mcp`, `run_headless` installs the fake store and live services.
**Demo:** a 2D and a 3D game built with no game C++ beyond its rules: an animated 2D character with a sheet, a camera that follows and shakes, a one-shot sound and a particle burst on pickup, a 3D character controller walking onto a dynamic crate pile, an enemy prefab placed five times by MCP and an agent-painted tilemap level.
**Gates:** every new asset type round-trips through MCP, cook and editor unchanged; a capability table generated from the code (component, asset type, MCP tool, editor panel, doc section per feature) has no "C++ only" row left that the audit marked as a gap, and CI fails when a new component is not registered in `engine_components.cpp`; replay hashes hold; `local_ci.sh` green on every step.

### M-AGENT — AI-native, human-free game development · **size L–XL (rough guess, ≈ 150–250 h engineering, not estimated per step)** · tier: off-tier tooling, gates nothing

*Added 2026-10-14 by the user's request: the engine should let one agent, or several working together, build and finish a game with no human in the loop. The blind test (Lamplighter), the dogfood games (Prism Break, Undertow) and Kindle's MCP authoring show where agents still lean on a person or a workaround: they cannot see a frame over MCP (user guide 14.5), every code change means a manual build plus a server restart, gameplay checks need a hand-written autoplay flag, the docs ship partly outside the SDK, and two agents cannot safely edit one project. M-DATA-REACH gives agents the hands; this track gives them eyes, a feedback loop and a way to share work. In-game AI (LLM NPCs) stays out of scope (M10+).*

**Builds, in order:** (1) eyes: `render_frame` (the M4.5 stretch item) returning an MCP image of the open or a saved scene at tick N with scripted input, from any camera or a free one, at a chosen resolution and safe area; `render_sheet` for a contact sheet of several ticks or cameras; a software fallback so it works on a GPU-less cloud box; `image_diff` against a saved golden with a score · (2) a closed code loop: `module_build` compiles the game module, returns compiler diagnostics as file:line:col JSON and hot-reloads it, so new components and systems appear without restarting the server; `module_test` runs the module's tests · (3) playtesting without a person: `.mctest` scenario assets (scene, scripted input or a built-in bot, ticks, assertions on component values, events and the log) run by `test_run`, plus a `trace` option on `run_headless` that samples chosen fields every N ticks; generic kit bots (walk to target, explore, button masher) so a game needs no custom autoplay; a fun/feel report from bot runs (time to finish, deaths, stuck spots, idle time) · (4) self-contained knowledge: the user guide, kit docs, component schemas, worked sample games and recipes served as `mce://docs/...` resources and searchable through `docs_search`, all shipped in the SDK; MCP prompts for "start a game from a brief", "add a level", "polish pass"; `engine_capabilities` lists what each feature is reachable through (the M-DATA-REACH table) · (5) content without a human: bundled CC0/OFL starter libraries (fonts, sprite sets, sound effects, music loops, skyboxes, materials) searchable through `library_search` and copied into a project with their credits written automatically; procedural generators as tools (palette, pixel sprite, tile set, sfxr-style sound effect, noise texture) · (6) quality gates an agent can run: `project_check` (broken or unused references, missing credits, sRGB on data textures, scenes that fail to load, performance budget from headless metrics, accessibility basics such as text size and contrast), `ship_build` with the smoke run and the zip path returned · (7) several agents on one project: more than one open document per server, an MCP session per agent with its own undo history, asset-level locks or optimistic versions with merge of `.mcscene` / `.mcprefab` edits by entity name, a project event feed (`project_watch`: who changed what) and a shared task file (`.mctasks`) agents claim work from; scenes split into prefabs and chunk scenes so agents work in parallel · (8) a feedback loop into the engine: a `report_friction` tool that appends structured friction notes to the project, collected by `mce` for the engine's own backlog.
**Demo:** from a one-paragraph brief and an empty SDK project, with no human message after the brief, (a) one agent and (b) three agents working in parallel (level, code, art and audio) build a shippable 2D game and a small 3D game: playable title, levels, win and lose, credits, a passing `project_check`, `.mctest` suites green and a shipped zip; the run's transcript, contact sheets and friction log are stored as the record.
**Gates:** the blind test re-run on a fresh agent that has never seen the engine source finishes with no workaround the friction log marks as blocking; `render_frame` output is checked against goldens in `local_ci.sh`; the multi-agent run produces no lost edit (conflicts are reported, never silently overwritten); determinism holds for every tool that runs the sim; `local_ci.sh` green on every step.

6. **No silent scope change**: any slip enters the milestone doc as a slip note; cuts execute the pre-agreed ladder without re-negotiation.
