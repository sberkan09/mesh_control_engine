# Technology Panel — Candidate: `cpp-modern-gpu`

**Position:** C++23 with a hand-written RHI over raw Direct3D 12 (first) and raw Vulkan 1.3 (second).
**Candidate stance:** maximum control, maximum industry-standard skill transfer, honest about solo-dev cost.

---

## 1. The committed stack (one decision per row, no option lists)

| Load-bearing choice | Decision | Why this and not the alternative |
|---|---|---|
| Language | **C++23**, MSVC 19.40+ (Visual Studio 2022) primary; Clang 18+ checked in CI for cross-platform sanity. **No C++ modules** — plain headers, `#pragma once`, PCH + unity builds for compile time. | Unreal, Unity's native core, Decima, Frostbite are all C++. The entire games-industry toolchain (PIX, RenderDoc, VS debugger, ETW, vcpkg) assumes C++. C++23 is the sweet spot today: `std::expected`, `std::print`, `std::mdspan`, deducing `this`, and `if consteval` are real and shipped in MSVC; C++26 reflection is not usable yet, so we hand-roll reflection (below). Rust/Bevy would teach a different (valuable) ecosystem, but the stated goal is industry-standard engine skills — that is C++. |
| Graphics | **Custom RHI ("MCRhi") over raw D3D12 first** (Agility SDK, SM 6.6+), **Vulkan 1.3 as the second backend** added at milestone M2 to prove the abstraction. Shaders: **HLSL 2021 compiled with DXC** to DXIL (D3D12) and SPIR-V (Vulkan) — one shader source, two targets. | This is the same proven trick used by multi-backend engines (The Forge, Halo's tooling, Blender's backends): DXC's SPIR-V codegen means we never maintain GLSL *and* HLSL. D3D12 first because the dev box is Windows 10 and PIX is the best capture tool in the industry, period; its debug layer is precise, and the API is smaller than Vulkan's (no instance/physical-device dance, no extension lottery). Vulkan second because D3D12-first forces the RHI to be "modern-explicit-shaped" already (explicit queues, fences, descriptor management), which is exactly the shape Vulkan has. Adding Vulkan validates the abstraction instead of designing for a hypothetical. |
| RHI shape | Bindless-first: single large descriptor heap (D3D12) / descriptor indexing with `VK_EXT_descriptor_indexing` (Vulkan), GPU-visible descriptor indices in root constants. Render-graph (frame graph) layer above the RHI for transient resource aliasing and barrier placement. PSO/`PipelineStateCache` keyed by hash. | Bindless-only is *less* code than emulating D3D11-style binding models, and it is where the industry went (Unreal's SM6.6 bindless, id Tech 7, Cyberpunk's update). A render graph is the single highest-leverage architectural idea of the last decade (see the classic *FrameGraph: Extensible Rendering Architecture in Frostbite*, GDC 2017; Bevy's render graph). Writing both backends raw is where the deep learning actually happens — no wgpu-style safety layer will be imported. |
| Windowing / input | **SDL 3.x** (Zlib license) for window, input, gamepad, clipboard, DPI, file dialogs. | Explicitly within the from-scratch ethos: OS-level single-purpose libraries are allowed, and hand-rolling Win32 raw-input + XInput/GameInput + WM_DPICHANGED + multi-monitor DPI is pure yak-shaving with near-zero learning value. SDL 3 (stable since early 2025) is C, tiny, and keeps Linux plausibility free. Raw Win32 stays a documented fallback for the 3% of cases SDL obscures. |
| Audio | **miniaudio** (single-header, public domain) for device I/O only; **the mixer, voice management, DSP chain, and resource streaming are written from scratch** on top of its data callback. | miniaudio is exactly the "small single-purpose OS-level library" the ethos permits: it abstracts WASAPI/XAudio2/ALSA/CoreAudio so we don't write five backends. Everything audible (voice pools, sample-rate conversion, low-pass for occlusion, streaming buffers) is engine substance we write ourselves, following the well-documented design in *Game Engine Architecture* (Gregory, ch. 13) and Gaffer On Games' audio scheduling notes. FMOD/Wwise would violate the ethos; XAudio2 alone would be Windows-locked. |
| Editor UI | **Dear ImGui (docking branch)** for the entire editor and in-game debug overlays. A custom retained-mode vector UI for *shipped games* is deferred and designed later. | ImGui is the de-facto standard for engine tools (used internally at essentially every mid-size studio; the docking branch powers real production editors). It is immediate mode, which pairs naturally with a frame-based engine loop, and it frees us to spend editor budget on the *hard* parts: gizmos, prefab/scene serialization, asset browser, undo/redo. Its default look is a con; we mitigate with theming + custom font atlas. Editor authority principle: **the editor owns the canonical scene representation; the runtime never edits** (the Godot/Unity model). |
| ECS | **Custom archetype-based ECS written from scratch**, using EnTT's sparse-set ideas and flecs' relationship/`isa` model as design references (read Skypjack's *ECS back to basics* series and the flecs docs; do not link the libraries). | The ECS *is* the engine's intellectual core — outsourcing it (EnTT/flecs) would outsource the main learning objective. An archetype (table) layout gives cache-friendly iteration like Unity DOTS; archetypes + sparse sets for lookups is a well-understood design with real reference implementations to study. flecs' relationship model is adopted as a phase-2 feature (parent/child via archetype edges) rather than importing flecs. |
| Physics | **3D: Jolt 5.x** (MPL 2.0; the physics of *Horizon Forbidden West*, *Death Stranding 2*, and Unity 6's default). **2D: from-scratch narrowphase + solver** (swept AABB + circles, sequential-impulse solver à la Erin Catto's Box2D GDC slides). | Jolt is the strongest "single-purpose library" case in the panel: deterministic, cache-optimized, actively maintained, and reading its source is a masterclass. Writing a competitive 3D physics engine solo is a multi-year project that would kill the engine goal; writing a *2D* solver is a contained, high-learning-value project (Box2D's core is ~accessible) and keeps the from-scratch muscle exercised. A thin `RigidBody2D`/`Collider2D` component layer maps 2D onto the ECS. |
| Math | **Custom math library**, right-handed, Y-up, meters, radians, column vectors, column-major storage. SIMD paths behind a scalar-first implementation, verified against DirectXMath in unit tests. | Math is small, stable, and the conventions decision (handedness, units) infects every other subsystem, so owning it matters. glTF is right-handed Y-up; D3D12 doesn't care as long as we're consistent and account for the NDC z-range difference ([0,1] in D3D vs [-1,1] in GL/Vulkan) in one projection-matrix function per backend. DirectXMath stays as the test oracle, not the dependency. |
| Reflection & serialization | **Hand-rolled reflection**: a macro + `constexpr` trait system that walks fields (name, type, offset, flags), used by the editor inspector, scene serialization, and asset headers. C++26 static reflection adopted later if/when MSVC ships it. | Every engine hand-rolls this until C++26 (Unreal's UHT, Havok's RTTI). The macro cost is bounded (~1 line per field) and the editor depends entirely on it, so it must be ours. |
| Asset pipeline | Two-stage: **source assets → offline "cook" → custom binary `.mce` containers** (magic + version + CRC + aligned payload), loaded memory-mapped at runtime. Importers: **custom glTF 2.0 importer** (JSON + base64; spec is small and unambiguous), stb_image for PNG/JPG source decode, **ispc_texcomp** for BC7/BC6H compression at cook time, **meshoptimizer** for vertex-cache/index compression at cook time (Tom Forsyth's vertex-cache algorithm), WAV for audio sources. Shaders cooked to DXIL/SPIR-V blobs in a shader archive with source-hash dependency tracking. | Cooked-binary-only is the id Tech / Unreal / Destiny model: the runtime never parses JSON or PNG, which keeps load code trivial and hot-reloadable. glTF 2.0 is the right interchange format (industry standard, text-diffable, spec is genuinely small); writing the importer is a week, not a quarter, and teaches the real asset problems (normals handedness, skinning, PBR parameters). meshoptimizer + ispc_texcomp are cook-time-only single-purpose tools — the ethos cost is zero because they never ship in the runtime. |
| Memory | Custom CPU allocators from scratch: frame-linear allocator (reset per frame), pool allocators, TLSF general-purpose fallback; **D3D12 Memory Allocator (AMD)** for VRAM initially, own VRAM budgeting later. | The allocator zoo is standard engine curriculum (Gregory ch. 6). D3D12MA is quasi-mandatory infrastructure (placement/placed-resource bookkeeping is enormous); hand-rolling it teaches little and delays everything else. |
| Concurrency | **Custom job system from scratch**: thread pool with job graph (dependencies) first; fibers later if profiling demands (reference: Christian Gyrling, *Parallelizing the Naughty Dog Engine Using Fibers*, GDC 2015). No Intel TBB / no BS::thread_pool. | The job graph is engine substance and a top-tier learning artifact. The render thread is split early (record on worker, submit on main) but a full multithreaded renderer is explicitly *not* an M1 goal — D3D12 command-list model makes the upgrade path real when we get there. |
| Build system | **CMake 3.28+ with presets, Ninja backend, VS 2022 generator for debugging**, dependencies via **vcpkg manifests** (pinned), unity builds + PCH for compile time, **GitHub Actions** CI (windows-latest, clang-tidy + warnings-as-errors). | CMake is the industry lingua franca and the 5-year-viability choice; presets kill 90% of its ergonomics pain. xmake/Meson are nicer but hire-ability and ecosystem support favor CMake. No MSBuild project files — the build must be scriptable from day one. |
| Profiling / debugging | **Tracy** (zone profiler, in-house client integration) + **PIX** for GPU captures + D3D12 debug layer + **RenderDoc** as secondary GPU debugger. | Tracy is the modern standard for engine frame profiling (used by many indie and AA engines); PIX is simply the best D3D12 tool that exists. Both are single-purpose and ethos-compatible. |
| Scripting | **Deferred, decided now**: Lua 5.4 embedded via sol2 in phase 2, for gameplay scripting and modding; gameplay itself stays C++ components until then. | A bytecode VM from scratch is a wonderful *stretch* project but must not block the engine; sol2+Lua is the lowest-risk embeddable choice with proven engine usage. Recording the decision now prevents architecture drift (e.g., accidental C++-only gameplay assumptions in the serializer). |
| VCS / docs | git + Git LFS for binaries; every subsystem ships an ADR (architecture decision record) under `docs/`. | Cheap, standard, and the LFS-free workflow (text-first assets) stays fast. |

## 2. Milestone plan (honest solo-dev pacing, ~10–15 h/week)

- **M0 (months 1–2):** window (SDL3) + D3D12 device + swapchain + colored triangle + SPIR-V/DXIL DXC pipeline + Tracy wired. *The D3D12 bootstrap is the single steepest learning cliff in the plan; budget it explicitly.*
- **M1 (months 3–6):** custom ECS + math lib + sprite/batched 2D renderer + ImGui editor shell (entity list, inspector via reflection) + scene save/load. **Shippable 2D game #1 becomes possible here.**
- **M2 (months 7–12):** glTF importer + cooked mesh/texture formats + 3D PBR forward renderer (IBL, cascade shadows) + render graph + **Vulkan 1.3 backend to validate the RHI**.
- **M3 (months 13–18):** Jolt integration + 2D physics + miniaudio mixer + job system + asset browser + prefab system.
- **M4 (months 19–24):** editor maturity (gizmos, undo/redo, multi-document), lighting/shadow polish, GPU-driven culling experiments.
- **M5 (year 3+):** ship a small complete 3D game; revisit VRAM allocator, fibers, and game-UI.

## 3. Risks, stated plainly

1. **D3D12/Vulkan boilerplate is the biggest schedule threat.** A raw-backend triangle takes weeks, not days. Mitigation: M0 is timeboxed and PIX unblocks faster than any other API's tooling would.
2. **From-scratch ECS + renderer + editor simultaneously is the classic solo-dev death spiral.** Mitigation: hard milestone gates; each M must end in a runnable thing.
3. **Two RHI backends double testing cost.** Mitigation: Vulkan is a *validation* of an already-working design, deferred to M2, never blocking gameplay milestones.
4. **C++ compile times** erode iteration speed. Mitigation: unity builds, PCH, pimpl across module boundaries, no templates in hot interfaces.
5. **ImGui's look** is not a shipped-game look. Accepted: the editor is a tool; game UI is a separate, later system.

## 4. Summary argument

This stack buys the two things no other candidate can: (a) the graphics layer is *ours* — bindless, render-graphed, multithread-capable, learned the hard way on the two APIs that run the actual games industry; and (b) every hour spent transfers directly to studio jobs, because D3D12/PIX/HLSL/CMake/C++ are the daily bread of professional engine teams. The cost is real: this is the slowest path to a visible result on the panel, and it only works with milestone discipline and a ruthless "single-purpose library, never an engine" dependency rule.
